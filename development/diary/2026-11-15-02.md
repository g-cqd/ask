| Claim | Probe | Verdict |

| Those tests are slow on the runner | the same job on `68294d98` and `e8327348` | **Fails**: they pass there in seconds. What changed in `3a042633` is two tests, mine |

| The rewritten tests can fail | shellcheck started after the parse, and awaited before a parse failure is answered | **Holds**, on the second try: both fail by their time limit after 64 s. The first try hung for good: awaiting an unstructured task's value is not cancelled by a time limit. The test now lets its fake go when it is cancelled |

The mechanism: `CommandCheck.run` starts a `Process` and reads it to its end inside a task, so it holds one of the threads every
task of the process shares for as long as the program runs. The check's own programs take milliseconds. My tests ran scripts that
waited, on purpose, for up to 30 s (a fake shell until shellcheck had started; a fake shellcheck until the test let it go), each
holding a thread while what would release it waited for a thread. On this Mac there are ten such threads; on the runner, three.
Raising the patience from 3 s to 30 s to survive a slow runner is what turned two failing tests into a stalled process.

So the tests no longer run programs. `CommandCheck.check` takes the function that runs one (`Runner`, by default `run`), and the
tests give closures that wait on each other as tasks do, holding nothing: the parse ends only once shellcheck has started; a
parse failure is answered while shellcheck still waits. Two more pin what the seam could now get wrong: each part's arguments,
input, environment and deadline, and a late part leaving the command unchecked.

One failure under the probe is the probe's own: with the variable set, `ReadSandboxTests` fails because the variable reaches the
`git` the test's command runs, which traps (`Trace/BPT trap: 5`). It passes without it.

Open, not touched: `CommandCheck.run` holding a shared thread is how it has always worked, and `GitQuery` and the forge's child
(`ForgeSnapshot.read(by:)`, up to twelve seconds) run through it. On a machine with few cores a slow `git` or a slow GitHub holds
one of few threads. `AemiRuntime.BlockingOffloadPool` and ask's own `DetachedThread` are both made for this.
