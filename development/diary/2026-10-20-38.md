# Diary — 2026-10-20 (38)

## 0042 begins with a defect in what already ships

The first probe for strict modes was a Swift build under a workspace-only write scope. It failed, but not for
the reason expected: `sandbox-exec: sandbox_apply: Operation not permitted`. SwiftPM compiles a manifest inside
its **own** `sandbox-exec`, and Seatbelt does not nest.

## Evidence

| Claim | Probe | Verdict |
|---|---|---|
| `swift build` works under ask's default sandbox (research table, 2026-10-19) | The same profiles, with a nonce comment making each manifest new to SwiftPM's cache | **REFUTED**: every profile, the default included, fails on a fresh manifest |
| The earlier pass was the manifest cache | A cached manifest builds under every profile; changing one comment makes it fail | CONFIRMED |
| SwiftPM has an environment switch to skip its sandbox | `strings` of swift-build and swift-package: every `SWIFTPM_*` variable listed; none disables it | REFUTED: only the `--disable-sandbox` flag |
| `--disable-sandbox` keeps ask's protections | A manifest reading a protected file, under ask's profile: `DENIED`; the same manifest unsandboxed: the secret | CONFIRMED |
| Under ask the model is told what went wrong | Before: the protected-path note, which misleads. After: a note naming the nested sandbox and the flag | Fixed; real-binary probe M |

So the research claim was wrong in the way the probe rules warn about: green for a reason other than the one
believed. It meant `ask` could not build a new Swift package, or one whose manifest it had just edited, unless the
model guessed the flag. That includes ask developing ask after a `Package.swift` change.

## Fix

- The bash tool says, on `sandbox_apply: Operation not permitted`, that a program tried to start its own sandbox,
  that SwiftPM takes `--disable-sandbox`, and that ask's sandbox still applies. The protected-path note is not used.
- The policy summary in the system prompt says so up front, so the model need not fail first.
- No note when the run is unsandboxed: it would claim a sandbox that is not there.

Red: three new tests failed for the right reason (the real failure, wrong note; no prompt sentence). Four compiling
mutants caught. Real-binary probe M: a fresh package fails as a nested sandbox with the new note, and
`swift build --disable-sandbox` builds and runs it under ask's sandbox.

## Cost, and a microbenchmark that misled

The system prompt grows by one sentence (cached). Every sandboxed command's output is now checked for two strings.
A standalone `String.contains` over 1 MiB took **20 ms**, which suggested switching to `ByteSearch` (1.3 ms for both).
The real path disagreed: a new benchmark, `tools/bash 1 MiB output sandboxed`, p50 **8.78 ms on main** and
**8.58 ms** with both checks, the same as `echo` under the sandbox. The standalone measured a string the tool never
scans in that form; I did not isolate why. The rewrite was not made (ADR-0016: a change that moves no number is not
kept); the benchmark stays.
