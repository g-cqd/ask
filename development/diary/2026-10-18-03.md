# Diary — 2026-10-18 (03)

Part 3.

## A decision made comfortable, then unmade

The terminal stack went into Aemi, and then came out again, within the same session.

I had landed `AemiTerminalCore` in Aemi first (`03ac1d5`), added the oracle (`e86d8fd`), and only then
asked where the terminal should live at all. The honest answer took a probe to reach, and it reversed
the decision.

Aemi's manifest describes itself as the kernel package and splits its targets into kernel runtime
tiers and application tiers, keeping them deliberately apart. Terminal is neither. It is an escape-
sequence grammar, a capability negotiation, a reset lifecycle — a third category that fits inside
neither list. Containing it would have stretched a boundary Aemi already has to defend.

The second argument was stronger than the first: Aemi has **zero tags**. Terminal work is the
fastest-moving thing in the ecosystem, and I had quietly parked it inside a repository that has never
published a release.

## Where I was careful not to overclaim

It would have been easy to write this up as "TerminalKit no longer depends on Aemi, problem solved."
That would have been false, and the ADR says so instead.

`AemiKernel` is zero-dependency, but SwiftPM resolves a package's entire manifest no matter which
target you link — so any consumer of `AemiKernel` resolves swift-syntax 603..<605 and its macro tree
regardless. And once the Atelier extraction lands, TerminalKit *will* import `AemiKernel`, so it will
depend on Aemi. The separation buys an independent cadence and a focused manifest. It does not buy
independence, and the decision record would be worthless if it pretended otherwise.

The name followed from the same reasoning: `TerminalKit`, not `AemiTerminal`. With its own repository,
an `Aemi` prefix asserts an ownership that no longer exists.

## What moving cost, honestly

A few hours of churn — two commits in, one revert out — to correct a placement I had already made. The
temptation was to leave it and call it forward progress. The cost of being wrong about where a shared
library lives compounds across every project that adopts it, so the churn was the cheaper half.

The real costs of the new repository are still unpaid and are listed in its ADR: TerminalKit must
recreate the swift-format, SwiftLint and CI setup that Aemi provides.

## Still owed, in order of how much it matters

1. **No real-emulator verification.** `kitty @ ls` returns `open /dev/tty: device not configured`.
   kitty 0.49.2 is installed; this session simply has no controlling TTY. The tiers are verified
   against a model of a terminal, not against a terminal. That is the single largest gap between what
   the reset ladder claims and what has been shown.
2. **No GitHub remote for TerminalKit.** Until one exists, `ask` can only reach it by a local path
   dependency, which does not ship. I am not creating a repository unasked.
3. **No performance number measured.** Cold start, idle memory, input delay, action-to-action delay.
   Unchanged, and still blocking any decision that wants to cite "ultra-performance".
4. **The ladder is not applied anywhere.** No teardown, no signal handler, no escalation trigger — a
   correct value nobody calls yet.
