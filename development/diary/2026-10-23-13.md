# Diary — 2026-10-23 (13)

## 0054: where ask's own startup CPU goes, five refuted levers, and one that works (ADR-0065)

Worktree `ask-startcpu`, from `8bdcea6`. Direct commands only. Diary 09 left "cut startup CPU" as the real lever because the
efficiency-core penalty scales with CPU time. This slice measures where that CPU goes and changes what the numbers justify.

## Sizing: what a launch costs before ask's own code

Interleaved fresh launches to exit, child CPU from `rusage`, host load 15-45 (so only differences between interleaved
programs mean anything; every column below comes from one interleaved run):

| Program | CPU p50 (IQR) |
|---|---|
| C hello | 1.78 (1.64-2.07) |
| Swift stdlib hello | 1.84 (1.70-2.16) |
| Swift + Foundation hello | 3.83 (3.42-4.43) |
| ask, exits before parsing (`--noop`, temporary entry) | 7.71 (6.70-9.33) in a run where Foundation was 4.80 |
| ask `--budgets` (parse and print) | 9.22 (8.39-10.85) in the same run |

So about **2.9 ms of CPU is spent in ask's binary before any of its code runs**, and parsing the command line adds about 1.5.

## Five levers, each tested and refuted

| Claim | Probe | Verdict |
|---|---|---|
| Chained fixups cost more than classic binds | relink with `-Xlinker -no_fixup_chains`; confirmed `LC_DYLD_INFO` replaced `LC_DYLD_CHAINED_FIXUPS` | **REFUTED**: 7.93 vs 7.66 ms CPU, 120 interleaved rounds |
| ask pays for an async `main` | Foundation hello with and without async `main` | **REFUTED**: 5.08 vs 4.90 ms, about 0.2 ms |
| The extra libraries ask links explain it | a hello that really uses Synchronization, System, os, CryptoKit, RegexBuilder and Foundation (16 libraries, ask has 20) | **REFUTED**: 4.65 vs 4.16 ms (+0.5), against ask's 6.42 |
| Applying fixups dirties many pages | minor faults of C / Foundation hello / ask `--noop` | **REFUTED**: 319 / 595 / 610; the 2.2 ms gap has almost no extra faults |
| A size-optimised build has fewer fixups | `-Xswiftc -Osize` into a separate scratch path | **REFUTED**: larger binary (11.79 vs 11.09 MB), 18,633 vs 18,753 fixups, 5.22 vs 5.24 ms CPU |

Two measurement mistakes are kept here. A first build failed on a missing import and my `cp` ran anyway, so I briefly held a
**stale** binary that still printed the old argument error; the check on its output caught it before any number was used.
The first fixed-work control ran 180 ms of compute and showed only 3%, which could never resemble a 10 ms launch.

## The profiler

`xctrace record --template 'Time Profiler'` works here without elevated permissions; its `dyld-library-load` table was empty
for these launches, so the `time-profile` samples were used. Sixty launches of `--noop` (one failed to record and is not
included) gave **413 samples**, classified by frames present in the stack, so categories overlap only where a stack holds both:

| Where the samples are | Share |
|---|---|
| dyld resolving imported symbols (binds) | 25.7% |
| initializers (libSystem, libdispatch, objc, CoreFoundation) | 24.2% |
| other dyld | 19.1% |
| frames with no symbol name | 10.7% |
| finding, loading and mapping libraries | 7.7% |
| Swift runtime / ask code | 4.6% |
| applying fixups / rebases | 1.0% |

The single top leaf is `mach_o::GenericTrie::find`, 13.8%: the loader looks each import up in a library's export trie on every
launch, and ask imports **2,020 symbols** (1,359 from libswiftCore) against 14 for a Foundation hello. The initializer share is
paid by any Foundation program. Only the import resolution is ask's, and cutting it means a smaller binary surface, which no
build setting tried here achieves. Sample counts are small (about six per launch), so shares are good to a few percentage points.

## What works: skip ArgumentParser for a bare launch

ArgumentParser reflects over `Ask`'s options and seven subcommands on every launch, including the one with no arguments. ADR-0065:
the launch moves into a plain `LaunchRequest`; a bare `ask` builds the default directly; any argument takes the parser path as
before. `--help`, the option errors, `ask sessions` and `ask config` print byte-identical output to the baseline.

The repository bans `CommandLine.arguments` in `Sources` (ADR-0015), so the guard gained one named exception, for counting in
`Sources/ask/Ask.swift` only, with a test that fails if it is used for anything else. A second source-scanning test keeps the two
paths the same launch (every option defaults to "not given", and `LaunchRequest` mirrors each one). Six mutants of these guards,
each of which makes a bare launch or the exception wrong, are caught by their intended assertions; sources were restored.

### Measured

Baseline and candidate both built from the same tree at `8bdcea6` (the candidate differs only by this change), copied before
anything could overwrite them; 80 alternating pairs per cadence; every launch completed; host load 6.6 to 21.

| Cadence | CPU saved per launch, paired median [IQR] | pairs where the candidate is cheaper | cold wall saved |
|---|---|---|---|
| paced 350 ms | **0.92 ms** [0.00, 1.70] | 76% | 0.81 ms, 63% of pairs |
| burst | **1.11 ms** [-0.86, 3.10] | 66% | 0.84 ms, 57% of pairs |

The CPU saving is consistent (about 7% of a launch). The wall-time saving points the same way but is within noise, so it is not
claimed. Absolute times were far over the cold limit on this loaded host for both binaries (candidate burst p50 27.1 ms, baseline
29.7 ms, load up to 21), and the burst run exited non-zero for that reason. That is the efficiency-core and load effect of diary
09, not a verdict on the change.

## Verification

Full gate: 87 + 176 + 70 + 337 + 558 tests (the Core bundle gained the three guards), formatting, strict lint and analyzers pass.
A fresh `swift build -c release --product ask` is **byte-identical** to the measured candidate (sha256 prefix `6674712000e3`,
11,198,896 bytes), and all ten real-binary suites pass on it: agent-run, anthropic-env, connections, folding, input, interactive,
model-lists, pointer, quota and thinking. No fixture leftovers.
