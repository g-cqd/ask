# Diary — 2026-10-28 (07)

## Copilot images and the VS Code request shape (roadmap 0084)

Owner: "copilot support of images is the second most important one", and "our copilot sign in uses vscode impersonation techniques
as well so we should match what vscode sends for such request". Source read: `microsoft/vscode-copilot-chat` 0.44.0 (the version
ask claims), `sst/opencode` and pi's installed package. Machine load was very high (load average 28–59 on 8 cores).

### What VS Code sends for a request with a picture

- Header `Copilot-Vision-Request: true`, only when a message holds an `image_url` part **and** the model has `supports.vision`
  (`chatMLFetcher.ts`). opencode sets the same header by scanning the body (chat `image_url`, Responses `input_image`, Messages
  `image` including one nested in a `tool_result`).
- Chat headers: `Authorization`, `X-Request-Id`, `OpenAI-Intent`, `X-GitHub-Api-Version: 2025-05-01`, `X-Interaction-Id` (one per
  user prompt; `startInteraction()` runs when a chat turn begins), `X-Interaction-Type` and `X-Agent-Task-Id` (the request id) for
  agent interactions, `X-Initiator` (`user` or `agent`).
- Responses: a tool result's pictures go in a following user message `[{input_text: "Image associated with the above tool call:"},
  {input_image, detail: "auto", image_url}]`. Messages: the image is a base64 block inside the tool result.
- VS Code does not resize (`ImageServiceImpl.resizeImage` returns its input). For chat and Messages it first **uploads** a
  tool-result image to a GitHub attachment endpoint (`RequestType.ChatAttachmentUpload`, from the closed `@vscode/copilot-api`
  package) and sends the returned URL, falling back to base64 on failure. The endpoint is not in the repo, so ask cannot match it
  and uses VS Code's own fallback (base64).
- It checks the image count only for Gemini-family models (`max_prompt_images`).

### What the live catalogue says (`ask models copilot-vscode`)

Every model reports vision. `max_prompt_images` is 1 for most (haiku-5.5 and sonnet-5.5: 5), `max_prompt_image_size` is about 3 MB
(3145728), media types are jpeg, png, webp, gif and, except kimi-k3, pdf. ask's own default of 4.5 MiB would exceed the size limit
and a long session would exceed the count, so both limits are now read and applied.

### Changes in ask

- `ImageLimits` (count, bytes, media types) on `CatalogModel`, `ResolvedModel`, `AgentSettings` and `ToolContext`; parsed from
  Copilot's `limits.vision`; shown in an IMAGES column of `ask models`.
- `read` fits the picture to the model: `ImageReader.Allowance` bounds the bytes and the media types (a PNG over the limit becomes a
  JPEG; PDF pages and video frames too).
- `ImagePart.filtering` also replaces a picture of an unlisted type, and, past the allowance, the oldest pictures (down to half of
  it, so a cached prefix survives a few turns). Default allowance when a provider says nothing: 20 (a guess).
- Copilot requests: `Copilot-Vision-Request` when a message holds an image; chat requests now carry VS Code's `X-Interaction-Id`
  (new per user-initiated request, kept for the tool calls after), `X-Interaction-Type`, `X-Agent-Task-Id` (equal to
  `X-Request-Id`) and `X-GitHub-Api-Version: 2025-05-01` (was `2025-10-01`, which the 0.44.0 source does not use; the catalogue
  request keeps its own value). OpenAI chat and Responses pictures carry `detail: "auto"`, and the follow-up lead is VS Code's.

### Live check (the first real image requests of this work)

A 64×64 red PNG read through the `read` tool, with the new headers: `claude-haiku-5.5` (Messages), `gpt-6-luna` (Responses) and
`kimi-k3` (chat completions) each answered "Red". A 3.3 MB noise PNG on haiku-5.5 was sent as a 1.1 MB JPEG (the 3 MB limit) and
described correctly.
