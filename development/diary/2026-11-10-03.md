# 2026-11-10 (03): word-aware input painting and editing (n57, t249)

## Claim: the input hard-wraps words, and painting alone cannot safely change that

`PromptLayout.frame` and `PromptEditor.moveVertically` both construct TerminalKit's InputLayout with hard wrapping. One map must
serve both, or Up/Down, clicks, selection and display can disagree. The optional upstream mode is pinned at b692bf8.

- `swift test -c release --enable-testable-imports --force-resolved-versions --filter WordWrappedPromptTests`: four tests,
  eight red issues before adoption. `hello world` became `hello wo` / `rld`; the click used the wrong word-row offset.
- After both call sites opt in: all four pass, including dragging across a soft wrap copying `lo won`, without an added newline.
- The surrounding navigation, viewport, wheel and click suites pass too: 38 tests. Existing no-space hard-wrap behaviour remains.
- SwiftPM's Xcode backend ignored an editable dependency in this run and read the old checkout. A temporary local package path
  allowed early integration tests; it is removed in favour of the published full revision. No local-path dependency ships.
- The personal SSH key was loaded with `ssh-add --apple-use-keychain /Volumes/Personal/Github/ssh/gcqd_github` and upstream
  b692bf8 was pushed only after TerminalKit's quality/release gate passed. The owner's local TerminalKit main is untouched.

## Measured cost

Upstream `Scripts/measure-word-input.py`: nine interleaved pairs, 100 layouts each, actual sources compiled with swiftc -O.
ASCII prose (~6.6 KB): hard median 30.4 us (30.2–32.0), words 176.1 us (174.0–185.5). Mixed CJK/combining/emoji:
hard 199.7 us (193.3–209.1), words 281.1 us (274.2–313.1). This is added feature cost, not a speedup; the machine was shared.
ask caches layout while only the cursor moves. Original whitespace and newlines are preserved; long words keep hard wrapping.
