# Diary — 2026-10-20 (50)

## The screen selects, copies and scrolls with the pointer

First ask code over TerminalKit's regions and selection (roadmap 0051, TerminalKit 0016 and 0017). The pin moved from `ac898fd` to
`bfd65f5`. Scope: the **transcript** only. Nothing folds yet, nothing is clickable but the selection, and no `ui.*` key exists, so
`ScreenOptions` carries ADR-0046's defaults (mouse on, copy on select on, three lines per wheel step).

### What was built

- **A row says where it came from.** `ScreenComposer` wraps with `TextWrap.rows`, so each transcript row records its item (the block),
  hard line, grapheme offset and starting column, and the text without the prefix some rows carry (`› `). Provenance is not part of what
  a row *shows*, so a row that only moved is not rewritten.
- **The frame reaches the mouse.** The render thread draws and the loop that handles the mouse is another thread, so the composer
  publishes each frame's `RowMap`, the transcript size and its line count through a `Mutex` box. A click means what was drawn, and a
  selection is anchored in content, so a frame of lag changes nothing.
- **The controller owns the pointer** as state in, state and effects out, like the keyboard: `PointerRecognizer` and
  `SelectionController` live in it, the wheel moves `scrollback` (never past the top), a drag starting in the transcript selects, a
  drag at the first or last transcript row scrolls one line, a double click takes a word and a triple click a line, a key or a paste
  clears the selection. `.copy(text)` is a new effect.
- **The highlight** is the selected cells drawn inverse, in the row's own style, nothing else (the owner's rule: nothing painted).
  `ColumnSlicer` cuts the row at the columns, wide graphemes whole.
- **The copy** is TerminalKit's plan carried out by `ScreenClipboard`: the OSC 52 bytes to the terminal, and `pbcopy` (off the caller's
  thread) where the terminal is not known to take them, never over ssh. A test supplies its own pasteboard, so the suite never touches
  the owner's clipboard.
- **The terminal is asked for mouse reports** (`TerminalModes.mouse`) unless `ScreenOptions.mouse` is off, and gives them up on every
  exit path.

### What went wrong

- **A real bug, found by a test:** `copyIfCommitted(selector.click(...))` read `self` before evaluating the argument that changes
  `selector`, so a double click copied the *previous* selection: nothing on the second click, and the word on the third. Swift evaluates
  the receiver first. Fixed by binding the update to a local; the same shape in `dragEnded`.
- **A kit bug, found by the same screen:** `RowMap.position` gave the first column no grapheme under it for the trailing edge, so a drag
  backwards from column 0 lost its last character (TerminalKit `bfd65f5`, its diary 6).
- **One mutation survives and cannot be killed:** making the composer rewrite every row every frame changes nothing observable, because
  `ScreenBuffer` does not dirty a cell written with the value it already holds. The composer's own row skip is a CPU saving only, so
  no test at the output can assert it. The dirty-row test checks the property that matters, what is written to the terminal.
- Two of my own test expectations were wrong (a blank row after scrolling; where a backwards drag ends) and the code was right.
- One mutation did not compile and was redone, the fifth time in this work.

### Not verified

- **No real terminal.** Everything above is the controller driven with reports and a buffer read back. Whether a physical drag in kitty,
  Ghostty, WezTerm and Terminal.app selects the same text, and whether the clipboard ends up with it, is the real-terminal probe still
  owed in roadmap 0051.
- **Autoscroll moves only while the pointer moves.** A terminal reports nothing for a pointer held still at the edge, so holding the
  pointer there does not keep scrolling. A timer would, and was not built.
- **Nothing says it copied.** There is no status text; a failed `pbcopy` is silent.
- **With copy on select off there is no way to copy**: the selection is highlighted and nothing takes it. A key for that is owed.
- **The prompt is not selectable** (the selection model is the transcript's), and a click there only clears the selection.
- Performance of a frame with a selection on a long transcript was not measured; the composer does one `highlights` pass over the
  visible rows, which the kit measured at 36 to 58 µs for a screen.
