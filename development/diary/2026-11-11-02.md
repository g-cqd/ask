# 2026-11-11 (02): a clicked path carries its line and column (t215, roadmap 0216)

## Claim: an opener's `{line}` is always 1

**CONFIRMED** by reading and by test: a link's address leaves `:12:5` out (the terminal must be given the file alone), and nothing
else carried it. `LinkLocationTests` and `ClickedLinkTests`: eight issues red on stubs.

- The place is read from the row the link is drawn on, once per layout of the block: a reply's shortened path covers its place, a
  path in plain text is followed by it. `PathLinks.Link` holds it beside the address.
- Only a click joins them, as `file:///a/b.swift#L12C5`. A `#` in a file's own name is percent-encoded in the address, so the last
  `#` is always the click's. `ClickedLink` reads the place back and gives `{url}` the address without it; `LinkOpener` builds the
  file from the path, so the system's own opening is unchanged (`LinkOpenerTests`).
- A web link's `#…` is the page's and is left alone. Digits that are not a place (`a.swift: 12`, `a.swift:x`) are not one.
- Mine: the first run of the reply test failed because the rig set its "is it there" answer after the reply was laid out, so the
  relative path was not a link. The rig now sets it first.
- Not done: a path wrapped before its place opens at line 1.
