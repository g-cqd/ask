# 2026-11-14 (03): a library's errors printed over the screen

The owner's screenshot: under the input, `ask[62086:…] Error: execSQLStatement:… DB=/Users/gc/Library/Caches/ask/Cache.db …
cannot commit - no transaction is active`, over the status line. Two causes, both mine of the same night:

1. The process on screen (pid 62086, started 00:16) was a build from before security audit 3: its `#123` reads used the system's
   shared HTTP session, which keeps a cache in `~/Library/Caches/ask/Cache.db` and had it open. At 00:51, checking that the fixed
   build leaves no cache, I deleted those files under it. Its next cache write failed, and CFNetwork said so on standard error.
2. Standard error is the terminal the screen is drawn on, and nothing kept it off.

| Claim | Probe | Verdict |
|---|---|---|
| The running process had the deleted cache open | `lsof -p 62086`: `Cache.db`, `-wal`, `-shm`, `httpstorages.sqlite` | CONFIRMED |
| The current build opens no such cache | audit 3's check: a `#5` leaves none; `HTTPSessionStandardsTests` forbids another session | CONFIRMED earlier |
| No command ask starts inherits its standard error | read: every spawn names its own (`.combinedWithOutput`, `.discarded`, `.string`, `.sequence`) | read |
| A write to standard error from inside the process lands on the screen | a debugger's `write(2, …)` in the running installed build: on the screen | CONFIRMED |
| With `StandardErrorGuard` it goes to `stderr.log`, and nothing reaches the screen | the same on the new build: in the log, not on the screen | CONFIRMED |
| The guard sends, restores, refuses quietly, and its log starts again past 1 MiB | `StandardErrorGuardTests` (3; red with the redirection removed) | pass |
| `OS_ACTIVITY_DT_MODE` or `CFNETWORK_DIAGNOSTICS` make the libraries print | three runs: nothing printed | NOT REPRODUCED that way |
