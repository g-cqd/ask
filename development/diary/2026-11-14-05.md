# 2026-11-14 (05): six megabytes for a number in the status bar

Roadmap 0232 step 2. Entry 04 said idle memory was 17.3–17.9 MB and that the excess over 15 MiB was linking. That was measured
with a provider configured, in a folder that is not a GitHub repository. The gate, run in this repository, said 22.9 MB. The
difference is the finding.

| Claim | Probe | Verdict |
|---|---|---|

| The working directory changes idle memory | the gate's environment by hand, same binary, `/tmp` then this repository | **Holds**: 16,672 against 22,688 KiB; 660 mapped images against 668 |
| It is the GitHub origin, not the repository's size or its files | two empty repositories, one with `origin` on GitHub, twice each | **Holds**: 16,736 and 16,624 against 23,152 and 22,624 KiB |

The cause: roadmap 0186 (mine, two days ago) reads the open pull requests and issues and the branch's pull request at the start,
in process. The first request loads the system's network stack and it stays. ADR-0116 and roadmap 0143 had each removed exactly
this from an idle ask; the forge read put it back and no number noticed, because the budget was already over for another reason.

The owner's two decisions (asked, 2026-11-14): the read is done by a child process (ADR-0152), and the budgets are 24 MiB idle and
30 MiB active, resident (ADR-0151).

Not verified: the status bar's pull-request number through the child on a real branch with an open pull request (this
repository has none; the tests cover the value's path from the child's output to the screen's update). Not gated: nothing fails
if a later change loads the network stack at idle again while staying under 24 MiB; the image count above is the thing to compare.
