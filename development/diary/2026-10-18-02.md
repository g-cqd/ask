# Diary — 2026-10-18 (02)

Part 2.

## The seam was assumed, so it was measured

Roadmap 0001 said to move `KittyTerminal`, `KittyCodecs` and `KittyRenderer`. That was a reasonable
guess from the module names and it was wrong.

Grepping every import in those three modules found `KittyStyle` required by two of them and
`AtelierText` — which lives in a *different package*, `AtelierCore` — required by `KittyRenderer`.
Following the closure one level further pulled in `KittyInput`. The seam is six modules and 6,263
lines, not three and 3,530: **79% larger than the plan claimed.**

The result was good news in the way that matters. Every external dependency in the closure is either
standard library or `AemiKernel`, which is *already in Aemi*. There is no route out to `KittyEditor`,
which at 10,890 lines and sixteen dependencies is the application tier. The stack is genuinely
separable — but only once you measure which modules are inside it.

Two more assumptions fell the same way. Aemi is **one package with many targets**, as its own manifest
says, so `AemiTerminal` is a target group rather than a new package. And Atelier depends on Aemi by
**pinned revision** (`85065dc`), not by version — so the zero tags ADR-0001 called a blocker are not
one. The tags are still worth having; they just are not what is standing between these projects.

ADR-0001 is marked superseded by ADR-0004 rather than edited, because rewriting a decision record
until the evidence that changed it is invisible is how decision records become useless.

## A byte-exact test caught two real bugs, on its first run

`AemiTerminalCore` landed with the tiered reset ladder: selective cleanup, then DECSTR, then RIS, in
that order, because the ordering is the design. Nine tests, written first, confirmed red against the
missing API before any implementation existed.

One failed. Not a compile error — a genuine mismatch, one byte out of 64.

`ESC [ ? 1006 l` had been written as `1,0,6` instead of `1,0,0,6`, and `ESC [ ? 2004 l` as `2,0,4`
instead of `2,0,0,4`. Both are malformed, and both are invisible to inspection: they look like
plausible byte soup. Left in, a crash would have left the user with mouse reporting and bracketed
paste still switched on — precisely the failure the ladder exists to repair.

The interesting part is how long it took to *find* it. The obvious move was to re-read the two arrays
and spot the error; reading them three times did not surface it. Printing the actual bytes and
comparing index by index found it in one run. This is the white paper's rule paying for itself: I had
a claim ("these sequences are correct") that was only ever supported by my own transcription of it,
and the probe that could falsify it was not "read it again", it was "make the machine compare".

Also worth noting: the pre-commit hook **blocked** the commit on `swift-format` violations before I
saw them. A green test run is not a green commit, and the gap between them is where lint lives.

## Still owed, and not to be assumed

- **The PTY test.** Nine tests prove the bytes we emit. None of them prove that DECSTR preserves
  scrollback, or that selective cleanup really leaves no private mode set. That is the half a user
  actually experiences, and it is still missing.
- The ladder is not yet *applied* anywhere — no teardown, no signal handler, no escalation trigger.
  It is a correct value nobody calls yet.
- No performance number has been measured. Unchanged.
