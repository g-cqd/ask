# Diary — 2026-10-18 (12)

## Correct the signal safety claim before adding sessions

TerminalKit's published handler still acquired a Swift mutex inside its OS callback. The earlier
claim that this was async-signal-safe was wrong. TerminalKit ADR-0015 supersedes ADR-0013; a small
C shim uses always-lock-free atomics, preserves errno, and writes only to a nonblocking pipe. Swift
lifecycle locks and user callbacks run on the reader thread, never in the OS callback.

Additional regression: stopping an unstarted handler stopped the real owner. The test failed before
that fix. Eight Swift signal/lifecycle tests and the isolated C saturation probe now pass. The C probe
raises 100,000 signals before draining, verifies shutdown bits survive a full pipe, restores earlier
signal dispositions and rejects stale pending bits between generations. It runs in the quality gate.

Pin updated to `264f7448191b0d802db9f4a625a54d3d3064ddd7`; normal TUI return now stops its handler.

`python3 /tmp/ask-safe-signal-probe.py`, against a separate shipping release build, returned:

- SIGTERM: exit 143, ICANON and ECHO restored, alternate-screen exit and cursor-show emitted.
- SIGINT: exit 130, same terminal restoration.

The first harness waited for exit without draining PTY output. `sample` located the worker in
`tcsetattr(TCSAFLUSH)`: terminal output draining required the peer to read. Reading concurrently,
as a real emulator does, made both probes finish. That was harness backpressure, not lost delivery.
