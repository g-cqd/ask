# 2026-11-16 (03): codemode's known gaps

The owner's order (2026-11-16): close codemode's known gaps, then resume `ask serve`, then the red items of CI. One section a
gap, each landed and pushed by itself.

## A script that asks for more output than a tool's cap gets it

`max_output_tokens` may go to 100,000, and the tool cut the report to it; then the registry cut every tool's output again at
50 KiB and 2,000 lines (`OutputCap.standard`), so nothing past about 12,800 tokens was honoured, and a script of many short
lines was cut at 2,000 of them with no word of where the whole was.

| Claim | Probe | Verdict |
|---|---|---|
| The second cut is the registry's | `probe-codemode.py` part B on main's binary: 3,000 rows, 80,000 tokens asked for | **Holds**: 51,193 bytes reached the model |
| An output its tool bounded is left alone | `ToolRegistryTests`, `CodemodeToolTests`, red first; the same probe on the new binary | **Holds**: the 3,000 rows whole, over 200,000 bytes, in the model's next request |

Changed: `ToolOutput.bounded`, which a tool sets when it cut its content to a limit its caller chose; the registry's cap
leaves such an output as it is. `codemode` is the only tool that sets it.

## A script that is stopped keeps what it had said

A script stopped at its deadline or at its memory failed with "What it had said is lost.": what it said was held in its
process until it ended, and crossed as one line with `run`'s answer. A model that printed its progress and then spun learnt
nothing of how far it got.

| Claim | Probe | Verdict |
|---|---|---|
| What a stopped script said is lost | `probe-codemode.py` parts B and E on main's binary: say, then spin; say, then allocate (JavaScript and Python) | **Holds**: four checks fail, each with "What it had said is lost." |
| Told as it is said, it is kept | The same on the new binary, three runs | **Holds**: PASS three times; deadline, memory and Python's memory each end with what was said |
| The tests can fail | The VM not telling, Python not sending, the keeper's own cap removed | **Holds**: 43 + 4 issues, then green again |
| The host tells before the script ends, not at its end | `CodemodeHostTests`: a call answered only once the parent has heard | **Holds**: a host that told at the end would wait for its time limit |

Changed: each thing a script says is a `said` notification from its process to its keeper (`CodemodeWire.said`), in order;
`run` is answered with how the script ended and how many calls it left, nothing else. `CodemodeSaid` keeps what crossed, and a
process that says more than a script may (10,000 items, or four bytes a character of the megabyte) is stopped by the keeper:
the process holds itself to the limit, the keeper does not take its word. The failures no longer say that anything is lost.
The 8 MiB a line may be now concerns one thing said, not the whole.

Not measured again: the 11.5 ms a script costs. A script that says 10,000 things sends 10,000 lines where it sent one; the test
of that many items runs in the suite's 0.7 s with the rest.

## One Python allocation larger than the limit is stopped as it grows

A Python script watches its own peak size from a thread, and one allocation larger than the limit holds the interpreter's lock
while it is filled: the thread sees it once made (diary 2026-11-16-02). The keeper now watches the process from outside.

| Claim | Probe | Verdict |
|---|---|---|
| Another process's footprint can be read, under `sandbox-exec` too, and it is seen growing | A Python of 3 GiB in one allocation, read with `proc_pid_rusage` every 2 ms from its parent, three runs each way | **Holds**: first seen past 256 MiB after 25 to 28 ms, at 256 to 280 MiB; left alone it reaches 3,078 MiB |
| Ended there, it never takes the rest | The same, with `SIGKILL` at the first reading past the limit | **Holds**: peak 258 to 280 MiB, gone in 28 to 33 ms |
| Through ask, the allocation is made whole today | `probe-codemode.py` part E on main's binary, the script's peak read from outside every millisecond | **Holds**: 3,087 MiB, stopped after 1.42 s |
| With the keeper's watch it is not | The same on the new binary, eleven runs | **Holds**: 245 to 283 MiB as sampled, each PASS; what it had said is kept |
| The tests can fail | No child watched | **Holds**: `CodemodeWatchTests` and the Python test fail (4 issues), then green again |

Changed: `CodemodeChild.memory`, set for a child its keeper is to watch (Python; the JavaScript host watches itself, and no
lock keeps its thread from looking); `CodemodeWatch`, a thread of 64 KiB that reads the child's footprint every 2 ms for as
long as a Python script runs, tells the keeper why, and ends the process. The child is known by its id and by when it started,
so a process that took its id after it is gone reads as nothing and is not stopped. The script's own watch stays, for a system
that will not say what another process took.

Found on the way, by the tests under a one-thread pool (`LIBDISPATCH_COOPERATIVE_POOL_STRICT=1`): the watch first ended the
keeper's reading as it ended the process, and what the script had written just before was then not always read ("before" and
"a line" missing, one run). The watch now ends the process and no more; its end is what ends the reading, after the last line.
Seven runs under that pool since, none failing.

The peak in the probe is a sample each millisecond, so the true one is a little above it. Not measured: what the thread costs
a script in time; it reads one number 500 times a second, for Python scripts only, and idle memory has no part in it.

## The calls a script makes at once, beyond reads and commands

Reads and commands made at once had been probed; writes, edits, jobs and MCP had not. All through the real binary, a script
making sixteen or eight calls with `Promise.all` (`Scripts/probe-codemode-at-once.py`, new).

| Claim | Probe | Verdict |
|---|---|---|
| Sixteen edits at once to one file are all made | Sixteen markers in one file, one edit each; five runs on main's binary | **Refuted**: each said "Replaced 1 occurrence", and 2 or 3 of 16 were in the file, every run |
| Sixteen writes at once, each to its own file, all land | Sixteen files, their content read back | **Holds** |
| Sixteen writes at once to one file leave one of them whole | 400,000 of one letter each; the file read back | **Holds**: one letter, 400,000 of it, three runs (the write is atomic) |
| Jobs started at once are jobs of their own | Eight `bash` with `yield_seconds`, then eight `job` waits at once | **Holds**: eight ids, each wait returned its own job's line; 1.2 s for eight commands of 1 s |
| Calls at once to one MCP server reach it together | A stdio server that answers each call from a thread, after 0.5 s, and says when it arrived | **Holds**: eight arrivals within 1 ms, each answer its own, 0.51 s in all. The repository's fixture server answers one at a time, and took 4.06 s: that is the server's |
| Tasks added at once are all added | Sixteen `tasks` adds, then a read | **Holds**: sixteen, with sixteen ids |
| A model's own calls of one turn are not concerned | `AgentLoop.runTurn` | They run in order; only a script makes calls at once |

The one defect: an edit reads its file, replaces, and writes it back, and nothing kept two from reading the same text. Fixed
where it is: `EditTool` holds one lock from the read to the write, for every file (an edit takes about a millisecond).
`FileToolsTests`, 64 edits at once to a file of 2,000 lines: failed six runs of six before the lock, passes six of six with it.
The probe: main's binary FAIL (16 said, 2 made), the new one PASS three times.

Not covered: two asks editing one file at once, which are two processes and share no lock; nor an edit beside a `write` of
the whole file, where the last to write wins, as it does for a person.

## `ask serve`, resumed: an edit is told as a diff, and a call with the model's input

The owner's order: codemode's gaps, then `ask serve` (roadmap 0234, ADR-0154), then CI. Serve's tenth part.

| Claim | Probe | Verdict |
|---|---|---|
| A client is told what a `write` or an `edit` changes | `probe-serve.py` part A on main's binary: the `tool_call` of a write | **Refuted**: its content was the text written, and no `rawInput`; a client cannot draw a diff from that |
| An update's content replaces the call's (Tool Calls, "Updating") | The specification's page, read; not a client | **Read, not run**: so the diff is said again when the call ends, before what it returned |

Built: `ConversationUpdate.toolStarted` carries the input as the model wrote it, the bytes the call already holds, which the
screen does not read. `ACPToolCall` passes it as `rawInput` and, for a `write` or an `edit` of a file, says a `diff`:
`old_text` and `new_text` as they are, a whole file's `content` as `newText` with no `oldText`. A call that failed keeps no
diff. Three tests in `ACPToolCallTests`, broken once on purpose (the diff not repeated, the input not passed): 3 issues.
The probe: main's binary FAIL on the new check, the new one PASS twice.

A default taken in the owner's absence: a whole file written over an existing one is a diff with no old text, so a client
shows all of it as added. The old text is not known where the call is told, and reading the file there would be a second read
of what the tool reads. Open: what Zed draws for it, and whether other agents' adapters say the old text (unprobed).
