## What was built

Typing `@` at the start of a word lists the project's files above the prompt, ranked (path prefix, name prefix, name contains, path
contains), narrowed as you type; the keys are the `/` picker's. **Enter and Tab insert `@path ` and never send; nothing is read or
attached** (ADR-0069 decides this and says what attaching would change). A `:12-30` after the path is kept; a name with a space is
inserted quoted. A path typed in full closes the list, so Enter sends. Files the sandbox will not let ask read are counted in the
title and never named.

The listing is made off the input path: `ProjectLister` asks `git ls-files --cached --others --exclude-standard` (five seconds, own
process group), falls back to a bounded walk outside git, filters through the sandbox's read policy, and stops at 20,000. The
controller asks with an `indexFiles` effect and the answer comes back as a `ConversationUpdate`; until then the picker is one line that
takes only Escape. A listing older than ten seconds is asked for again while the old one keeps serving.

A refactor first (`PickerRow`, `CompletionPicker.Kind`), behaviour-preserving, committed alone.

## Probes, and what each refuted or confirmed

- **Confirmed** by a temporary timing test (since deleted): this repository's 936 files list in 26–125 ms warm (654 ms the first time);
  a 20,000-file plain tree takes 0.8–3.9 s to walk unrestricted and 1.1–1.9 s under the default sandbox. All of that is off the input
  path, which is why the picker has a placeholder and a thread of its own.
- **Confirmed** by `Scripts/probe-files.py` through the real binary and a PTY, in a real git repository with an ignored directory, a
  sandbox-denied directory, a name with a space and an untracked file: 17 checks, the negative control (the baseline binary shows no list
  on `@`) passes; includes a file created after the first listing, found once the listing is ten seconds old, and a screen of 11 rows
  where `@` stays text and Enter sends.
- **Refuted, my own plan:** ranking four ways per path was fine at 936 files and not at 20,000. Measured per key on the benchmark
  (below); a reorder that rules out non-matches first was worse for matching queries (2.8→2.2 ms for no-match, 2.4→2.9 ms for a common
  name, a pair of key and backspace); the fix was to search the whole buffer once.

## Mistakes

- **The `@` scan cost 16 µs a key in a long draft, and I had written "unchanged" before measuring it.** Measured against the baseline
  tree it was 51 µs against 35, twice. `utf8.contains` is the generic byte loop; `memchr` over the native string's storage restored
  35 µs. Now it is a measurement in the table, not a claim. The guard is an optimisation, so mutating it away changes no behaviour and
  no test can catch it (an equivalent mutant); the benchmark is its guard.
- Three mutant escapes were mine: no test of a name-prefix against a name that merely contains the query when the second was listed
  first; no test of a hit across two adjacent paths (the new search's own edge); no test of the fourth group at all. Each now has one.
- A mutant that replaced a group with `continue` looped forever inside the search and was a timeout, which proves nothing. Replaced
  with a mutant that puts the group in the wrong place.
- The driver's function grew past 60 lines; the effect switch became `perform`, and `ScreenSession` moved to its own file, which also
  retired the file's entry in the structure baseline (the ratchet only shrinks).
- Numbering collided with the clipboard work, as in diaries 11 and 16; fixed by renumbering the unpublished side.
