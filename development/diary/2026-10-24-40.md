# Diary — 2026-10-24 (40)

## The wheel scrolls a tall input — roadmap 0051 and TerminalKit 0019, ADR-0086

### What changed

- `ScreenState.promptScroll` overrides the window top. `PromptLayout` draws the kit's window, or, when scrolled, one at that row, and says
  whether the cursor is in it. `ScreenComposer.cursorIsVisible` makes the frame hide the terminal cursor when it is not.
- `scrollInput(_:)` moves the window a row a step, clamped to the draft's rows, for a draft taller than its window.
- Editing, clicking, dragging, shifted keys and pastes clear it (through the one call that drops selections, and the shifted-key path).

### Evidence

| Claim | Probe | Result |
|---|---|---|
| A step shows the row above or below; the cursor and text stay; the cursor leaves the screen and returns | `InputWheelTests` (9 tests, 11 cases) | Pass |
| Steps stop at both ends and bank nothing; a draft that fits scrolls the transcript; the transcript is unaffected over itself | same | Pass |
| A key, a cursor key, a paste, a shifted key and a click each end the scroll; a click lands on the drawn row | same | Pass |
| Real binary | `probe-input.py` (54 checks): three wheel steps over a ten-line draft show lines 6 and 7, the terminal's cursor is hidden, nothing is submitted, a key brings back the window and cursor, and the provider and session receive the draft with exactly the typed characters | Pass; with no wheel steps the first check fails |
| Other contracts | pointer 26/26, folding, code 9, runners 8 | Pass |

Eleven mutants of the new code in two rounds: reversed, three rows a step, no clamp at either end, scroll of a draft that fits, a key and
a click not ending the scroll, the cursor always drawn, the layout ignoring the scroll, the window top taken from the kit. Two survived
once and were informative: *a key keeping the scroll* was equivalent because typing already went through the call that drops selections
(so the explicit clear in the key router was removed, and the shifted-key path, which does not go through it, got its own and its own
test), and *no upper clamp* only showed as extra dead steps after overshooting, so the test now steps back once after going far past the
end.

### Costs

Head only, at a one-minute load of 30 (not paired, not quiet): keystroke frame 41 / 50 / 126 µs, streamed line 105 / 119 / 254 µs, cached composer
3,585 / 4,335 / 7,335 ns, unchanged ordinary frame 12 / 13 / 19 µs; allocations **identical to before** (7 for the cached composer, 3 for
the unchanged frame). Earlier quiet runs of the same harness read 32–35 / 82–88 / 3,167 / 11, so these figures are inflated by load as much
as by anything, and cannot show either a regression or its absence. The change adds one optional parameter and, when no scroll is set,
the same kit call as before; I did not run a paired A/B because the machine was too busy for it to mean anything.
