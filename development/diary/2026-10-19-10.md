## The lock, probed before it was written

Two terminals on one session would interleave two branches. ADR-0017 swaps the file for a new inode on every
repair, so a lock tied to the first file opened would stop protecting the session after the first repair.

`/tmp/flock-probe.py`, on macOS 27.2 and APFS:

| Case | Result |
|---|---|
| Another process, while the lock is held | refused (`EWOULDBLOCK`, 35) |
| A second descriptor in the same process | refused |
| Replacement locked before the rename | the path stays locked |
| Holder killed by SIGKILL | released |

The design that follows (ADR-0025):
- lock before reading;
- lock the replacement before the rename;
- after locking, compare the descriptor's inode with the path's.

Four mutations were caught: a shared lock, no inode check, no hand-over across a rewrite, and create without
a lock. Two other mutants did not compile, so they proved nothing. Typed throws do not pass through `||`'s
autoclosure.

## Cost (ADR-0016)

A new `session/create` and `session/open` benchmark was measured before the lock existed (p50):

| Benchmark | Before | With the lock |
|---|---|---|
| create | 55 µs, 3 syscalls | 55 µs, 6 syscalls |
| open, 10 entries | 41 µs, 5 syscalls | 53 µs at first |

Reading through the lock's descriptor instead of opening the file twice brought the open to 46 µs and 8
syscalls. That change was kept because it moved the number.

Noted for later: opening 1,000 entries (400 KB) takes 2.4 ms, about 2.4 µs per entry. That is fine for
resume, but it is the number to watch if sessions grow large.

## Mistakes

  instead of the verdict line. The message was reworded before anything left the branch.
- **The first `probe-interactive` D failed on "Resumed ".** The notice wrapped straight after that word,

  the session file only, which also reads better.
