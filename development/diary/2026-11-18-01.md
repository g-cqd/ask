# 2026-11-18 (1): Claude Opus 5.5 refused every request after ask's reconnection message

The owner: "ask is not resuming work with claude opus 5 5, why". The sunset session (`20261105T165936Z-08ffd7f4`) had answered
four requests in a row with `stop_reason: refusal`, no blocks and 0 output tokens. The first came after a dropped connection, and
the next three after a compaction. ask showed nothing for them, so to the owner ask looked broken.

## The probes

the copy's last compaction was edited: its `firstKept`, or the text of entry `20905`, which is the reconnection message
(`AgentLoop.reconnectionPrompt`) that ask recorded after the partial answer `20904`.

What triggers the refusal is "Continue exactly where it stopped, without repeating it … issue it again" placed after a partial
answer. A guess, not probed: it reads like the known trick of making a model finish a cut-off output. The refusal is the same
every time: the original wording was refused all 7 times it was tried.

## What changed

- `reconnectionPrompt` now asks the model to go on from where its incomplete answer ends, and to make an unreceived tool call again.
  The old wording stays recognised (`AgentLoop.earlierReconnectionPrompts`), so old sessions still replay a drop as a drop, and
  naming and `/resume` summaries still skip it.
- A response with stop reason `refusal` is now said: an error notice on the screen, live and on resume, and a line on standard
  error from `ask -p`. Before, it was an empty answer.
- The new tests were each broken once: with the old wording no longer recognised, and with the notice removed, they fail.

## Open

- Opus 5.5 still refuses in a session that already holds the old wording, until compaction drops it or the entry is reworded.
