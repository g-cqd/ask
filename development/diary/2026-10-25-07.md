# Diary — 2026-10-25 (07)

## An MCP client, first slice: the protocol and the stdio transport (ADR-0096, roadmap 0067)

The owner asked for "mcp". Before writing any code I read the project's decisions (ADR-0028: extensions are processes; ADR-0092: `mcp__*`
names kept whole) and probed what real servers do, because the specification and the servers differ (ADR-0096 has the table). Three
findings shaped the design: servers ignore `notifications/cancelled`, answer out of order, and a real suite exposes 207 tools.

## What was built

`Sources/AskMCP`: `MCPConnection` (requests matched by id, timeouts, cancellation, the server's `ping` and unknown requests, progress,
list changes, logs), the wire types, `LineSplitter`, `StdioLaunch` (minimal environment) and `StdioTransport` (session leader, grace
then signals, 64 MiB limit, standard-error tail). 61 tests in 8 suites, 1.1 s, stable over six runs. No tool is registered yet.

## What went wrong on the way

- A `#"…"#` literal holding a JSON Schema `"$ref":"#/$defs/n"` ended early at `"#`; two hashes fixed it.
- `initialized` was queued behind the connection's own writer, so a test saw it after the reply; it is now written before `start`
  returns, which is also what a caller needs to rely on.
- **Two transport tests hung** (timeouts, not failures). Cause 1: the writer task waited on a queue nobody finished once the child had
  died. Cause 2: closing waited for the child inside a task group, and awaiting a task is not interrupted by cancelling the waiter, so
  the stop after the grace never ran. Both are now structural (readers end the writer; a separate timer cancels the run).
- A message over the limit first looked fixed and was not: the reader ended but the child lived and the connection never learned. The
  body now leaves with an error, which stops the child.
- Mutation runs: the base was red once (the new test), so those results were thrown out and rerun on a green base.
