# 2026-11-15 (12): an animation tick copied the clock of every block the session had shown

From the owner's review of the running processes (`family/REVIEW-2026-11-15-performance-memory-settings.md`, section 4.2): in an
ask with a 16,000-entry session and one live block, 13 of 24 render-thread samples were freeing a dictionary of `BlockProgress`,
and 12 main-thread samples were in `Transcript.advanceProgress`. The owner chose to have ask's two items done now.

| Claim | Probe | Verdict |
|---|---|---|
| The render thread holds the last frame's state | TerminalKit's `RenderLoop.frame`: `lastState = state` | **Holds** |
| So a tick copies every clock, and the cost grows with the session | a transcript of N ended tool blocks and one live, a copy held as the render loop holds it, 300 ticks each replacing the held copy; release build | **Holds**: median 44 µs a tick at 1,000 blocks, 411 µs at 10,000, 1,447 µs at 35,000 |
| With the running clocks apart, a tick copies only them | the same, after | **Holds**: 1.5 µs, 4.0 µs, 7.0 µs. At 35,000 blocks, 200 times less |
| The clocks still answer as before | a differential test: 4,000 fixed pseudo-random steps (start, tick, end, start again where one ended, remove, clear) against one plain dictionary | **Holds**; red when a restarted clock's ended twin is left behind, and when an ended clock is not removed |

`ProgressClocks` kept one dictionary for every block's clock. A tick changes the live ones through it; the render thread shares
the dictionary through the last state, so the change copied all of it, and the copy it replaced was freed entry by entry on the
render thread (a clock holds a string). Note n55 had fixed the lookups (which blocks are live) and not the storage.

Now two stores: the clocks that run, and those that have ended. A tick changes the first, which is small; the second changes only
when a clock ends, is replaced or is removed.

What still grows with the session in a tick, measured above (1.5 to 7 µs): `Transcript.revisions`, an array of one integer a
block, copied the same way. At 35,000 blocks that is a 280 KB copy; left as it is.

Not verified: the running process. The numbers are of the transcript alone, in a test, not of an ask with the owner's session
resumed and sampled again; the mechanism is the one the review's samples showed.

## The session held decoded (the review's 4.1): measured, one part done

The owner chose: the search index's release now, the rest probed and put as a design first. Probes on a copy of the owner's
81 MB session (35,297 entries), in a release test process, footprint read with `vmmap --summary`:

| Claim | Probe | Verdict |
|---|---|---|
| The tree holds every payload | footprint before and after `SessionFile.open` | **Holds**: 8 → 116 MB |
| Most of it is of no use to the next request | the active branch from the last compaction on | **Holds**: 1,070 of 35,041 entries |
| The screen's copy is the smaller part | `history()` into a `ScreenController`, then both released | **Holds**: +38 MB for the 55,051 updates while they exist, +10 MB for the 29,994 blocks; 52 MB given back with the screen |
| The search index is large and cheap to read again | built, saved, read by a second `SessionSearch` | **Holds**: 62 MB once read, in 0.14 s; a search in a held index 3.7 ms. Its file is 70 MB, and building it peaks at +309 MB |
| Payloads could be read on demand at an offset | ADR-0138, read | **Fails** for compressed sessions: one deflate stream, restarted only when the file is reopened |

Done: `SessionSearch` lets its index go once the file holds it (`inFile`), and reads it again at the next search or update. One
that could not be written (no key open, no folder) stays, being the only copy. Three tests, red both ways: with the index never
let go, and with it always let go (an unwritten index was then built again at every search). A side effect, kept: an index
whose file was deleted is written again at the next search; held in memory, it never was.

Not done, and why: the tree's payloads and the screen's replay. They change what `SessionTree` is and what a resumed session
shows; roadmap 0238 has the numbers, what stands in the way and what to settle first, for the owner's reading.
