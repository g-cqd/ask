# Codemode: what pi does, and what each way of running a script costs here (2026-11-15)

The owner put codemode (roadmap 0012) first on 2026-11-15, "inspired by pi's integration": the model writes one script that
calls ask's tools, in parallel and in chains, and filters what they return before a compact result goes back into the context.
The surface is wanted in JavaScript (JavaScriptCore, bun or node) **and** Python. This note is the evidence gathered before any
design is put to the owner. Machine: mbp23 (M2 Pro), macOS 27.2. Probe sources: `development/research/probes/codemode/`.

## pi's codemode, as installed (1.4.0) and as run

Read: `@earendil-works/pi-codemode/README.md`, `pi-coding-agent/docs/codemode.md`, `dist/extensions/codemode/tool.js`.
Run: its `CodemodeSandbox` under node, against the cases below (`pi-edge-cases.mjs`).

- **The script** is raw JavaScript, the body of an async function: top-level `await` and `return` work. It runs in QuickJS
  compiled to WebAssembly, in a worker thread, about 17 to 20 ms an execution (47 ms the first).
- **Its only capability is the tools**: `tools.<name>(args)` returns a promise; no file system, network, timers, `require` or
  `process` (run: all `undefined`; `Date`, `Math`, `eval` exist).
- **Output**: `text(value)`, `console.*`, `image(...)`, a top-level `return`; `exit()` ends it successfully. The result the
  model reads starts with `Script completed` or `Script failed` and the wall time; several text items are each headed
  `==> text N/M <==`; console lines follow in one `<console_output>` block.
- **Nested calls go through the agent's own tool pipeline**: validation, hooks and permission checks apply exactly as for a
  direct call. Only the script's output reaches the model.
- **Failure**: a tool that fails rejects with an `Error` carrying its text; calls made before a failure are not undone; a call
  still running when the script ends is cancelled. Run: an uncaught failure is `script: no such file`; an unawaited call is
  `cancelled`; output written before a throw is kept.
- **Limits**: a hard deadline (`timeout_ms`, unset by default); 256 MB for the VM (run: `out of memory` at a 64 MB cap, in
  78 ms); output 16 Mi characters and 100,000 items, past which the script fails; the result is cut to `max_output_tokens`
  (default 10,000) keeping its start and end, the whole written to a file; two workers at most in a process; a promise nothing
  can settle fails at once (run: 17 ms, "waiting on a promise that can never settle"); `while (true) {}` ends at the deadline.
- **Options** on the first line: `// @options: {"max_output_tokens": 2000, "timeout_ms": 60000}`.
- **Across calls**: `store(key, value)` / `load(key)`, small JSON values kept in the session, written only when a script succeeds.
- **What the model is told**: the tool takes `{code}`; its description lists the callable tools as TypeScript declarations
  within a budget of 3,000 tokens, and `ALL_TOOLS`, `searchTools()`, `describeTool()` find the others. A setting presents the
  direct tools beside codemode (`on`) or hides them behind it (`only`). It is opt-in.
- Not for ask now: `models` (classifiers, image generation), the Cloudflare sandboxes, deterministic replay.

## What each way of running a script costs here

| Way | Probe | Start | A call | Stops a spinning script | Caps memory | Needs |
|---|---|---|---|---|---|---|
| **JavaScriptCore, in ask's process** | `jsc-in-process.swift`, `jsc-watchdog.swift` | 2 to 6 ms for a context | 0.4 ms the first, 0.02 ms each of 1,000; 100 calls of 30 ms in 40 ms | yes, with `JSContextGroupSetExecutionTimeLimit`, which is exported and not in the public headers | approximately: a watchdog asked every 20 ms stopped an allocating script at +477 MiB against 256 | nothing: a system framework. Linking it adds nothing to idle memory (5.6 MB, as Foundation alone); a live context is +3 MB |
| **bun, a child process** | `child-drive.py` over `child-prelude.mjs`, JSON lines on its pipes | 15 ms to ready (4.9 ms bare) | 1,000 in 6 ms; 100 of 30 ms in 40 ms | yes: kill | yes: kill | bun installed (it is, here) |
| **node, a child process** | the same | 104 ms | the same order | yes | yes | node installed |
| **deno, a child process** | the same | 25 ms | the same order | yes | yes | deno installed |
| **python3, a child process** | `child-prelude.py` | 14 ms bare, 21 with `json` and `threading`, **55 with `asyncio`** | 1,000 in 6 ms; 100 of 30 ms in 36 ms | yes | yes | python3 on the `PATH`; `/usr/bin/python3` is Xcode's shim (23 ms bare, 158 ms with asyncio) |
| pi's QuickJS, for scale | `pi-edge-cases.mjs` | 17 to 20 ms | | at its deadline | yes | node or bun |

What JavaScriptCore gives a script with nothing injected: no `fetch`, `require`, `process`, `setTimeout`, `XMLHttpRequest`,
`print`, `readFile` or `load`; `console` exists and prints nowhere; `WebAssembly` exists. So in process, a script can reach
only what ask hands it.

What it does not give: a way to notice a promise nothing can settle (the host has to count the calls it owes), a public way to
stop a script, any memory limit. Without a watchdog, a script asking for 4 GB got it in 0.4 s.

The time limit, probed: armed once, it calls back once; a callback that returns false is **not** asked again (the header
says it is). Re-armed from inside the callback, it polls: `while (true) {}` and a loop that catches everything were both
stopped at 0.52 s for a 0.5 s deadline, the exception being `JavaScript execution terminated.`, which a script cannot catch;
the context ran `1 + 1` afterwards.

## A child process needs a sandbox, and one is cheap

A child interpreter has the whole language: files, sockets, other programs. Under `sandbox-exec` with a deny-default profile
that allows reading and nothing else (four lines):

| | Probe | Verdict |
|---|---|---|
| Cost | `sandbox-exec … /usr/bin/true`, then bun and python3 under it | 9.0 ms alone; bun 11.2 ms, python3 21.2 ms in all |
| Writing a file | bun `writeFileSync`, python `open(…, "w")` | refused; no file made |
| The network | bun `fetch`, python `socket.create_connection` | refused |
| Running a program | bun `spawnSync(["/bin/ls"])` | **allowed** by that profile, which lets any program start: it would have to name the interpreter alone |
| Reading | python listing `~/.ssh` | **allowed** by that profile: reads would have to be narrowed to the interpreter's own files, or to what ask's `read` may read |

So "the only capability is the tools" is a property of JavaScriptCore in process by construction, and of a child process only
as far as its profile is right.

## What follows, before any decision

- **Python is a child process whatever is chosen for JavaScript**: there is no in-process Python worth having. So the bridge
  (a script's calls as messages on its pipes, answered by ask) is built either way, and AemiJSONRPC's serving connection is
  what it would be made of.
- **JavaScript can ride that bridge too** (bun, node, deno: one mechanism, a prelude a language, npm's and the runtime's own
  libraries, but a runtime to install and a sandbox to get right), **or run in process** (nothing to install, five times
  faster to start than the fastest child, tools-only by construction, at the price of a second mechanism and a private call
  for its limits).
- **`asyncio` costs 40 ms a script.** A Python surface that waits on calls with threads starts in 21 ms; one written as
  `await tools.read(...)` with `asyncio.gather` starts in 55.
- **Nested calls through ask's gate** cost what a direct call costs (the action budget, 8 ms, measured at 2 to 3.4 ms); the
  saving is the model's round trips, which are seconds each.

Not probed: bun and python3 under ask's own profile rather than a four-line one; a native built-in that does not poll
JavaScriptCore's watchdog (pi's notes say QuickJS on Bun has such); JavaScriptCore's behaviour when a context is released
while a call is pending; Linux, where there is no JavaScriptCore framework.
