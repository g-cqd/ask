Strict modes reached main as `81a6365`. This slice makes a resumed session keep the strict sandbox it ran under.

## A cost found and mostly removed

`session/open 1000 entries`, release, alternating rounds:

| Version | p50 [p25-p75], µs |
|---|---|
| main | 2,578 [2,533-2,638] and 2,619 [2,548-2,742] |
| record keys in the shared `CodingKeys` | 2,804 [2,705-2,988] and 2,742 [2,654-2,873] (+7%, separated) |
| record keys in their own key set | 2,685 [2,628-2,769] and 2,666 [2,589-2,771] (+2%, overlapping) |

**Refuted first:** that the larger enum case made every decoded line bigger. `MemoryLayout` says
`SessionLogRecord` is 160 bytes either way (`SessionEntry` dominates), so `indirect` would change nothing; reverted.
**Confirmed:** every key of every line was matched against two more coding keys. A separate key set for the record
removed most of it.

## An AemiJSON defect, reported

The separate key set was first written with a second keyed container in `encode(to:)`. Tests failed with
`encodingFailed`. A standalone probe at the pinned revision: Foundation merges two containers into
`{"extra":1,"type":"t"}`; AemiJSON emits `{"type":"t"{"extra":1}}`, which is not JSON, and with sorted keys throws.
Filed as g-cqd/AemiJSON#4 (the owner has someone fixing it). ask writes the record through one container of its own
key set, which is correct with or without the fix. Decoding through a second container works in AemiJSON.
