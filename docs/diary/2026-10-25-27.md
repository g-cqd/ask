# Diary — 2026-10-25 (27)

## Destructive tools are asked about (ADR-0110)

The policy ADR-0099 deferred, taken after the owner said continue twice with the item on the list: a tool its server marks
`destructiveHint` is put to the user before it runs, once a tool a session in the interactive screen; a one-shot run allows it.

## What was built

`DestructiveToolCall` and `ToolContext.destructiveApprover` in AskAgentCore; the ask in `MCPToolAdapter` and `MCPCallTool`; the mark in
`mcp_search`'s answer; the session grants and the question in the composition, through the existing approval screen (AskTUI needed no
change at all — its approval is a question and three keys). Two fixture tools that delete, and two probe sections.

## What went wrong on the way

- **A fixture bug of mine hung the whole suite.** I built the marked tool's JSON by appending `,"annotations":…` after the object's
  closing brace: invalid JSON, a reply that never answers the request, and `listTools` waiting on its timeout. Six tests "hung" with no
  output and I went hunting in the wrong place first (stale helpers from an earlier worktree's killed mutation run were still alive —
  worth remembering: `timeout` kills the shell, not the `swiftpm-testing-helper`).
- **Two stale-binary runs wasted time again**: assertions failing with text I had already rewritten, and a green run on a build that had
  not been made. Both caught because the failure output named old code; both runs thrown out.
- A batched edit spliced a fixture into nonsense because it matched an anchor I remembered instead of the file's text; the compiler
  caught it first. The repair is asserted this time.
- The screen probe raced itself: waiting for "Allow it?" matched the first question still on screen, so the zap check ran before the
  model had even called the tool. It now waits for the zap question's own words.
