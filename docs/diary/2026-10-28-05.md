### System API survey (apple-docs CLI, corpus snapshot-20260805-beta.2, macOS 27.0)

- `CGImageSourceCreateThumbnailAtIndex` with `kCGImageSourceCreateThumbnailFromImageAlways` "creates the thumbnail from the full
  image, subject to the limit specified by `kCGImageSourceThumbnailMaxPixelSize`". `…IfAbsent` would use a small embedded
  thumbnail, which is wrong for a model. ask uses `Always`.
- `kCGImageSourceShouldCacheImmediately` defaults to false ("decoding and caching happen only when you render").
- `kCGImageSourceSubsampleFactor` (2, 4, 8; JPEG, HEIF, TIFF, PNG; macOS 10.11+): "if the image doesn't support the factor, the
  source provides a larger or full-size image".
- `vImageScale_ARGB8888`: supports non-uniform scaling; the docs warn of artefacts with premultiplied alpha.

### Benchmark (loaded machine, load ≈ 32, `-O`, `/tmp/bench/b.swift`, synthetic photo-like images, scale to 2000 px, 3 runs each)

| Source | ImageIO thumbnail | vImage Lanczos (full decode, then scale) |
|---|---|---|
| 12 MP JPEG | 100–130 ms, 44 MiB | 180–220 ms, 114 MiB |
| 12 MP PNG | 370–490 ms, 86 MiB | 300–340 ms, 125 MiB |
| 12 MP HEIC | 290–345 ms, 46 MiB | 400–500 ms, 166 MiB |
| 48 MP JPEG | 165–170 ms, 56 MiB | 720–770 ms, 388 MiB |
| 48 MP PNG | 1.4–1.5 s, 148 MiB | 1.4–1.65 s, 434 MiB |
| 48 MP HEIC | 370–700 ms, 63 MiB | 1.3 s, 408 MiB |

Peak is `peak memory footprint` from `/usr/bin/time -l` for the whole process.

- **ImageIO's thumbnail path wins on speed and on memory.** It decodes at reduced size where the codec allows (JPEG, HEIC), so a
  48 MP JPEG costs 56 MiB where full decode plus vImage costs 388 MiB. vImage is only competitive for a PNG, which cannot be
  decoded at reduced size, and there it still uses 3× the memory. Kept ImageIO; vImage rejected.
- `ShouldCacheImmediately` made no measurable difference. Not used.
- **PNG encoding is the expensive step**: 260–350 ms and 3.2–4.9 MB for a photograph, against 10–30 ms and 0.35–0.7 MB for JPEG.
  pi's order (PNG first) would pay that on every photograph and send 6× the bytes. The reader now tries PNG first only for a PNG or
  GIF source or any image with transparency, and JPEG first otherwise. Same numbers, different order for photographs.
- A 48 MP PNG peaks at 148 MiB while it is read, far above the 20 MiB active-memory budget. It is transient and no codec path
  avoids it, but it is a budget exception to record in 0088. The file is also held twice (`[UInt8]` then `Data`).
