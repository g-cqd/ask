## Claims tested, including rejected explanations

| Claim | Probe | Verdict |
|---|---|---|
| The delay is waiting for the renderer's frame-rate limit | Read the pinned `RenderLoop` and record first output versus prompt/frame externally | **REFUTED** as proposed: the loop has no frame-rate timer, and most observed delay precedes terminal output |
| Model-list lookup or policy construction explains the bulk | Separate run/configuration/model/policy/instruction markers with wall and process CPU usage | **REFUTED for these samples**: configuration through model resolution about 0.13 ms, policy about 0.78 ms; most CPU precedes the CLI configuration marker |
| A no-argument parser bypass explains the large variance | Temporary no-argument entry delegates directly to the same configuration/screen; normal arguments keep ArgumentParser | **Not established**: about 0.75–0.92 ms difference in sequential samples, much smaller than the variance. Removed rather than add a second default-launch implementation |
| A task-group priority parameter raised startup priority | Log requested QoS and `Task.currentPriority` before entry, in the child, and at CLI configuration | **REFUTED**: the observed values stayed 21. That was not a valid higher-priority timing comparison; no compiler/runtime cause is asserted |
| An explicitly higher task priority removes the variance | A temporary `Task(priority: .userInitiated)` with bounded lifetime/cancellation; verify 25 in the trace, then 40 interleaved pairs | **REFUTED as a demonstrated fix**: default 13.18 ms [10.46–20.06], higher 12.70 [10.55–19.93], post-fork prompt medians/IQR. Wide overlap; priority change discarded |
| Slow starts simply ran on efficiency cores | SDK `pthread_cpu_number_np` snapshots plus current IORegistry cluster mapping | **REFUTED as a universal explanation**: one slow paced cohort sampled only performance CPU numbers. Later cohorts sampled both. A query is not affinity or a complete execution history |
| A missing literal trailing blank proves no prompt was rendered | Inspect the failed probe's raw bytes | **REFUTED**, as diary 04 records. `ask>` plus cursor positioning and the closing frame is valid output |

The temporary priority experiments were process-local probes, not a machine policy change. Both parser and
priority experiments were removed. A small, unisolated speed difference is not a causal solution to a large,
context-dependent startup range.

## Shipping versus instrumentation

A fresh shipping build at `de9e929` was copied before adding any probes. All subsequent measurements use fixed
copies, never a binary that a release-test or mutation build can overwrite.

The initial 30-start shipping burst (old post-fork boundary) measured prompt p50 **10.73 ms**, IQR **10.41–11.08**,
p95 **12.63**, range **9.58–24.81**; lifetime CPU p50 **10.09 ms**. It did not reproduce a 27 ms median. The existing
four-budget script then measured cold p50 **22.41 ms**, range **14.20–23.96**, on the same shipping artifact under
its different sampling cadence. That pre-correction clock excluded fork; it is not the final budget method.

An early paced/burst trace comparison showed process CPU before the CLI configuration marker at **14.71/6.07 ms**.
This identifies a region, not a unique dyld/Swift/hardware cause. No such cause is claimed from a timestamp alone.

The landed `Scripts/measure-startup.py` uses the corrected before-fork/full-frame boundary, fixed sample counts,
isolated configuration/state, child-side geometry, raw per-sample output, artifact-change detection and SHA-256.
It saves after every attempt. Instrumented or incomplete data cannot certify a shipping budget. Children receive
no prompt; the probe intentionally SIGKILLs and reaps only its own child after sampling its disposable PTY.

## Final shipping cohort and controls: the cause is still not found

After the last restore, an explicit `swift build -c release --product ask` (runtime sources byte-identical to
`de9e929`), then `Scripts/measure-startup.py .build/release/ask --runs 20 --idle-seconds .35`. All 20 frames
completed, no artifact change; **exit 1, over budget**: cold p50 **31.01 ms**, p25-p75 **30.09-31.44**, p95 **32.33**,
range **28.59-33.03**, lifetime CPU p50 **25.34 ms**, fork p50 3.20 ms. Host load **5.10 -> 4.70**, memory-pressure
level 2 (warning) before and after. This is a **tight** distribution, not scattered outliers, so it must not be
written off as noise.

Two controls, both run afterwards on the same host:

- A third same-artifact cadence cohort (40 pairs, host load 2.97 -> 3.90, pressure 2 -> 2) measured paced cold p50
  **13.98 ms** [13.26-15.16], max 95.64, versus burst **12.69 ms** [12.16-13.35]. Same artifact, same pressure
  level, same cadence as the 31.46 ms cohort - and passing. Load and the coarse pressure level do not cleanly
  separate the passing and failing cohorts.
- An unrelated fixed-work Python program (about 30 ms of integer work in a fresh process, 40 alternating paced/burst
  pairs, twice): paced wall p50 **35.79/33.99 ms** versus burst **32.43/31.01 ms**, CPU **31.71/30.92 versus
  30.09/28.63 ms**: an 8-10% idle-gap penalty. A first, 180 ms version of this control showed 3% and was **not**
  informative: long work amortizes any ramp, so it cannot resemble a 10 ms start. This does **refute** a plain "the
  idle gap makes all CPU work 2.5x slower" explanation; ask's observed paced/burst splits of 1.8x and 2.5x are not
  reproduced by generic compute.

So the data does not support "a host power-state effect" as the explanation, and it does not support "an ask
regression" either: ask's own phase timings (diary above) put most CPU before the CLI marker, and the same
shipping artifact has passed and failed on different runs. What is established: the failure is real and
repeatable at times, startup CPU time (not only waiting) is what grows, and generic compute does not grow with it.
Candidates not yet tested: page-cache or dyld shared-cache state of the 10.6 MB binary and its frameworks after
idle under memory pressure; per-launch dyld work that differs from Python's; thread-pool or Dispatch worker startup.
None is claimed. No threshold, OS setting or runtime code was changed.

Roadmap 0054 therefore stays **in-progress**: the measurement method is delivered and corrected, the cause is open.
