# Diary — 2026-10-20 (28)

## Steering and follow-ups, the next sequential unit

The user asked to go through the remaining work sequentially and merge each finished unit immediately.
The audit/repair notice reached main as `24603b2`; the benchmark pin repair as `15da901`.
This unit delivers queued input, leaving multi-line editing and session/model commands as 0045 and 0046.

Enter while a prompt runs queues steering; `/follow-up TEXT` queues a follow-up. Alt+Enter is a shortcut
when a terminal reports it as a modified key. Steering enters after the whole response/tool batch; follow-ups
only when the agent finishes. One per boundary, FIFO within each class, steering first.

The screen owns a pending copy until the loop acknowledges its persisted user entry. Normal completion
starts anything that raced with the last boundary. Abort or failure returns only unacknowledged messages
alongside the draft. These are not crash-durable drafts, and explicit quit discards pending input.

## Red and mutations

With the API stub accepting no input, the release tests failed on the missing user entries, request counts
and cancellation. Before the controller change its existing test failed on the missing queued notice.
After implementation the dedicated suites contain eight core tests and ten controller tests.

Fourteen distinct compiling mutations were caught, with the failure inspected:

1. Follow-ups eligible while work remains.
2. Follow-ups taking priority over steering.
3. Consuming a message without persisting it.
4. Leaving a persisted message queued.
5. Consuming input on the last turn, leaving no turn to answer it.
6. Removing the cancellation check before acceptance.
7. Leaving an acknowledged message in the screen's pending list.
8. Dropping a late message at normal completion.
9. Losing the unfinished draft on return.
10. Offering newly typed input to an aborting run.
11. Dequeuing before a write that fails.
12. Removing the executable's failure handoff: PTY L then sees a third request and an empty editor.
13. Making `/follow-up` steer instead.
14. Letting an empty follow-up start a model request.

Queue mutations 3, 4 and 11 were repeated after moving I/O outside its lock. Removing the final dequeue
initially failed compilation because the index became unused; that run proves nothing. A compiling variant
keeps the index used and fails both the remaining-queue assertion and the turn tests.

## Mistakes and limits

- The first benchmark filter, `loop/one turn`, selected no benchmarks. A zero exit with an empty report is
  not a measurement. All recorded runs use `loop/one turn.*` and contain actual sample tables.
- The first unfiltered run failed on a pre-existing stale `PipelineProbe.draw` call. Targeting the loop
  benchmark avoids that unrelated target; the failure remains reported.
- I initially matched tool labels against compact JSON, but the payload retained spaces. PTY J/K's three
  label checks failed while request/archive checks passed. Matching unique gate names, which never appear
  in the user prompt, fixed the probe; the whole suite then passed.
- The first live inspector guessed a nested `response.blocks` field. Session responses store `blocks`
  directly. The archive already proved success; after fixing the inspector the full live probe passed again.
- A 40-second attempted red test expired while still compiling; discarded. A subsequent built-test run
  reached the producer-during-write test and failed. That failure is not counted as an assertion-killed mutant.
- No new claim is made about the already-over-budget idle RSS, or about 0007's still-provisional budget.
- A terminal may intercept Alt+Enter or encode it ambiguously. The plain `/follow-up TEXT` path is tested
  on the real PTY too, so modified-key support is not required.
