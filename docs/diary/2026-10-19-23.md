# Diary — 2026-10-19 (23)

## The screen on TerminalKit's render thread (TerminalKit 0014, pinned at `74719fb`)

The user's direction: do not tie rendering to the main thread; input must never block and rendering must keep
going; stress-test the alternatives. TerminalKit did (its ADR-0026, `IsolationProbe`); this adopts the result.

**What changed:** `ScreenComposer` is a `FrameComposer`. The screen's loop applies each event to the state and
submits it; a `RenderLoop` draws the newest state on its own thread. Nothing in `runInteractiveScreen` is
main-actor isolated, and `RenderPipeline+Screen.swift` is gone.

**The edges the thread created, each handled and tested:**
- the session's keyboard-flag push and the frames share one terminal: `SerializedConnection`;
- the last frame is written before the terminal is restored, on a normal exit and on an error;
- a shutdown signal halts the render thread before it leaves the session, so no frame follows the restore.

## What it costs

At 120×40, `footprint`: **2,880 KB → 3,024 KB (+144 KB)**. Stack +32 KB (the render thread's, with the input
thread's, which landed earlier), malloc +80 KB, `__TEXT` +48 KB. RSS: 8,688–8,704 → 8,888–8,896 KiB, +190 KiB.
The idle-memory budget was already over; this does not change what it is measured against (roadmap 0007).

Frames cost what they did: the screen's own work is 0.1 ms, so at ask's load the thread changes nothing a user
feels. It is there for when the composer grows (highlighting, markdown) and for the day the main actor is
busy with something else.
