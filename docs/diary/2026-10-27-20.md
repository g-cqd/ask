### Implementation

- `ToolSummary.header` separates compact command/path/job targets from timeouts,
  yields, read windows, write byte sizes and replacement/action parameters.
  `fullInput` retains complete commands/content/replacements or original unknown-
  tool JSON. Legacy summaries remain for approval/log paths. Window arithmetic
  uses overflow-reporting addition rather than trapping on malformed tool values.
- Live and session-replayed events share `AgentConversation.map`, so both carry
  full input. Bash is presented as shell, while model schemas, persisted calls,
  tool dispatch and job identity retain their canonical names and IDs.
- Expanded tools render input above output in distinct labelled sections, including
  input-only calls. Decoration has no selection source. Canonical selected text
  contains the header, visible input, then output; source hard-line offsets and
  wrapped grapheme offsets match that projection. Empty output is labelled, not
  invented as copied tool data. Old items without input retain the older layout.
- A heredoc with more than 40 payload lines keeps its opener, first 20 payload
  lines, an omitted-count marker and closing delimiter. The marker opens only
  that heredoc; its opener refolds it. Ctrl+G operates on embedded folds independently
  of the whole-tool fold. Click ownership still includes the whole tool's padding.
- Supported forms are conservative literal cat/tee/interpreter commands with
  quoted/unquoted ASCII delimiters and optional tab stripping. Ambiguous forms,
  here-strings, comments, quoted redirection text and unterminated input stay
  fully visible. This is a UI projection, not a general shell parser. An
  unterminated literal opener preserves the remainder in one pass rather than
  rescanning every nested-looking line quadratically.
- Additional batch-review cases exercise common delimiter forms, multiple heredoc
  ordinals, click versus whole-block ownership, input copying without labels,
  and 1,000 unterminated opener-looking lines.

The first focused review exposed one overstrict test: a width-one layout cannot
fit a width-two grapheme without discarding text. The source-coordinate checks
still cover width one; the row-width assertion allows that indivisible grapheme.
No renderer behavior was changed to make the assertion pass.

### AemiRegex investigation and adoption

The user asked to investigate AemiRegex instead of Swift Regex, then requested a
repo-wide migration item. Read the resolved package's README, Pattern string API,
and manifest. The existing resolved revision `4ddbcd4…` provides linear-time
`Pattern` with captures over String/Substring. The heredoc opener pattern needs
neither backreferences nor lookaround. It uses that engine directly; no new regex
engine or generic parser was copied into ask. An explicit root dependency/product
uses the already resolved revision; no package revision changed.

A release comparison linked the shipping AemiRegex objects into a standalone
probe (`/tmp/ask-heredoc-regex-comparison.swift`). Fourteen opener cases agreed
with Swift Regex for both match presence and every capture, including Unicode
file names and rejected forms. Twenty alternating batches of 1,000 searches,
identical varying subjects and checksum 26,000, gave ns/search:

- AemiRegex p50 1,007.271; p25–p75 73.083–1,669.792; p95 2,615.833.
- Swift Regex p50 1,970.751; p25–p75 1,766.833–2,051.375; p95 5,436.250.

Command: `swiftc -O -I .build/out/Products/Release -Xcc -fmodule-map-file=.build/out/Intermediates.noindex/GeneratedModuleMaps/CAemiRegex.modulemap /tmp/ask-heredoc-regex-comparison.swift .build/out/Products/Release/AemiRegex.o .build/out/Products/Release/CAemiRegex.o -o /tmp/ask-heredoc-regex-comparison && /tmp/ask-heredoc-regex-comparison`.

This is evidence for this opener pattern/corpus on this host, not a universal
engine speed claim. Roadmap 0077 tracks the remaining repository-wide migration,
including parity, bounded failure, replacement semantics and benchmarks. Roadmap
0059 now points to the owner's concrete engine choice instead of waiting on it.
No existing unrelated Swift Regex use was silently rewritten in this batch.
