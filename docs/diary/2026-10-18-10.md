# Diary — 2026-10-18 (10)

## Two things I got wrong this session, both caught

## `NSLock` — a banned construct, written by me

The signal tests used `NSLock` in two helpers. Our own rule bans `NSLock`, `os_unfair_lock`,
`pthread_mutex_t` and serial `DispatchQueue` in favour of `Mutex`/`Atomic` from `Synchronization` —
and TerminalKit's own `POSIXTerminalConnection` and `SignalHandler` already use `Mutex` for exactly the
state they guard. I had the pattern in front of me and still reached for the Foundation class.

Replaced with `Mutex`, which also removed the `@unchecked Sendable` I had been relying on: with a
`Mutex` inside, `FailingConnection` is genuinely `Sendable` rather than asserted to be.

**A grep now finds no banned construct in `ask`** — the only remaining mention is the comment explaining
why it is banned.

## The macOS 26 floor was not being used, and the replacement table does not apply

I had been reading the guidance table — "`Mutex`, `Atomic` → `OSAllocatedUnfairLock`" — as if the
primitives were unavailable. **That table is the fallback for a floor too low to permit them.** Our
floor is macOS 26 (ADR-0003), and they are all present. Probed by compiling against
`-target arm64-apple-macos26.0`:

| Primitive | Status | Spelling that works |
|---|---|---|
| `InlineArray<N, T>` | available | `InlineArray<8, UInt8>([0x1B, …])`, `.span` |
| `Span` | available | `array.span`, `inlineArray.span` |
| `RawSpan` | available | `RawSpan(_unsafeBytes: UnsafeRawBufferPointer)`, `.byteCount` |
| `Mutex`, `Atomic` | available | `Synchronization` |

`RawSpan` took four attempts — the compiler's note (`candidate expects value of type
'UnsafeRawBufferPointer'`) is what found it. Worth writing down, because guessing the spelling wastes
more time than the lookup.

### A negative result worth keeping

**`InlineArray` buys nothing in `ask` right now.** The instinct is to make the reset-ladder and startup
sequences `InlineArray` literals instead of computed properties rebuilding a heap array — but
`TerminalConnection.writeContiguous` takes a `ContiguousArray<UInt8>`, so converting at the boundary
allocates anyway. The win is zero at the only place it would be paid.

That is a negative result with teeth: without it, the next person performs the same pointless
conversion. Where `InlineArray` *does* pay is inside TerminalKit, composing and comparing byte
sequences without a `ContiguousArray` round trip per step. That is TerminalKit's work.

## TerminalKit's `SignalHandler` cannot fire from a blocking read — and installing it is worse than the bug

Wiring `ask`'s signal shutdown and probing it on a PTY with a real `SIGTERM`:

| Configuration | Result |
|---|---|
| no signal handler | killed by `SIGTERM` — dies, terminal **not** restored |
| `SignalHandler` wired | **ignores `SIGTERM`** — still running after 4 s |

`DispatchSource.makeSignalSource(signal:queue:)` is given `.main`, and `ask`'s main thread is blocked
inside `read(into:)`. The main queue never runs, the `AsyncStream` never yields, and the process stops
responding to `SIGTERM` entirely.

**This is the second time this session a primitive that returns successfully turned out to do nothing**,
after the harness that reported PASS while every tier ran as a no-op. Same shape, same lesson: something
that appears to work and does not is worse than nothing, because it reads as handled.

So the wiring is reverted. `SignalShutdown` stays as the tested model of what must happen — nine tests,
guards probed both ways — and the wiring is recorded as blocked on a TerminalKit fix, because a signal
installer is generic and the white paper puts generics in the shared package. The fix needs to deliver
the signal off the main thread; a `sigaction` handler draining into a `Task` would do it without
`DispatchQueue`, which this project also bans.

Roadmap `0006` moves to `in-progress` with the blocker named.
