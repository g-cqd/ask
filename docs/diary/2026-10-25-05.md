# Diary — 2026-10-25 (05)

## `/fork`: a new session from this one, or from before a prompt (ADR-0094)

The other half of the session-tree pair, after `/tree` (diary 04). The data structure already had `fork`; the work was making a fork
that can stop at an earlier entry without moving the original, and the command around it.

## What was built

`SessionFile.fork(upTo:to:)`: copies the tree, moves the copy's leaf, forks that, carries the strict sandbox record across, and begins
the new file; `fork(to:)` is now `fork(upTo: leaf, to:)`. `SessionRecorder.fork(upTo:to:)` makes the recorder inside the lock. `/fork`
and `/fork N` in the composition root, with `/resume`'s switch rules.

## What went wrong on the way

- **The fork dropped the sandbox record.** `SessionTree.fork()` builds a tree from entries and leaf only, so the strict sandbox a session
  ran under was lost; a forked session would have resumed without it, which is ADR-0045's exact point. A test found it before the code
  did (I wrote it from the ADR, not from the implementation); the fork now carries it.
- **The concurrency checker refused to return the new file** across the recorder's lock, three ways (a result tied to `file`, a value
  made inside, a result sharing the original's injectable system calls). The last one was a real design smell: a fork inheriting the
  original's test seams. It uses the real calls now.
- **`~Copyable` in a tuple** is not supported, so my test helper became a function that fills a file in place.
- A mutant that did not compile, and one that was not a mutation at all (it changed nothing); dropped, not counted.
