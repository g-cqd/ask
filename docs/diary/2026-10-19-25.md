# Diary — 2026-10-19 (25)

## The sandbox: ask's own files and the secret stores (roadmap 0017, 0018; ADR-0035)

The user's next step in the agreed order. It closes what ADR-0032 and ADR-0034 both flagged: nothing stopped the
model from writing ask's config, running `ask trust` with a pty, or reading the credentials. The work is one
policy applied by the file tools and by `bash` under Seatbelt; either half alone protects nothing.

### Probes first, and what they found

- **A path rule is not enough.** Renaming a protected directory's parent away, editing the copy and renaming it
  back left the config tampered. Fixed by denying unlink and rename of every ancestor, which is what a rename is,
  and by making anything read-denied unwritable (or `~/.aws` could be moved and read under another name).
- **Three more ways round it in the in-process checks:** a dangling symlink into a protected directory,
  `..` after a name that does not exist yet, and the case-insensitive volume. All closed, all tested on a real file
  system.
- **`git` and a full `swift build` still work** under an allow-default profile with denials, which decided the
  default shape.
- **The cost is `sandbox-exec`, not the profile.** An empty profile costs the same as ours (9.9 against 10.2 ms).
  The recorded candidate (a launcher calling `sandbox_init_with_parameters` then `exec`) measured 11.3 against
  10.8 ms, so it is rejected. Net: about +8 ms per command.

### Built

`CanonicalPath`, `PathScope`, `SandboxRule`, `SandboxPolicy` (with an intersection that only narrows), the default
policy, `SeatbeltProfile`, `FileTools.authorized`, bash under `sandbox-exec`, the refusal note, the system prompt
line, `--no-sandbox`, and the `sandbox` config section with `allowRead` (user's file only) and `denyRead`.

### What the checks found

- **The probe's `HOME` was ignored.** The first run of the real-binary probe left `~/.aws` readable: ask used
  `NSHomeDirectory()`, which does not follow `$HOME`, while a command's `~` does. Protecting only one home is a
  hole, so both are covered. This is a real defect the probe found, not a probe error.
- **Two failures were my tests.** One put the "outside the scope" target under the temporary directory, which a
  strict scope allows on purpose; another asserted a refused `..` path would resolve. Fixed by moving the target
  (`/Users/Shared`) and by using a `..` after an existing directory.
- **The full disk.** Halfway through, the disk filled (100%, 116 MB free) and the writes of two files failed
  silently inside a heredoc. I stopped, checked each file's integrity against its expected contents, freed only
  what I had created, and asked before touching anything else. The space came back from elsewhere. Lesson: a
  failed write inside a `cat >` is silent unless the next step checks it.
- **Mutations.** 22 caught on the policy, compiler and tools, and 5 more on the configuration (relaxing
  `allowRead`, lifting ask's own directory, relative paths, accumulation, tilde expansion). Three results are not
  "caught" and are not claimed as such:
  - the bound on following dangling links is an equivalent mutant: the kernel's `ELOOP` ends a loop first, so
    the counter is unreachable in practice. It stays as a cheap bound, with a comment saying so;
  - "edit does not check reading" escaped, because anything unreadable is also unwritable, so the write check
    refuses first. A test now pins the *message* (reading is the problem), which is the part that differs;
  - "I/O on the unchecked path" escaped because only a race between the check and the use tells the paths apart.
    A test pins the contract instead: `authorized` returns the canonical path.

### Live

With the real model and a harmless canary planted in ask's real config directory:
- `bash cat` and `bash echo >` into it: `Operation not permitted`;
- the `read` tool, by absolute path and through a symlink in the working directory: refused with the sandbox's
  message, and the canary text appeared nowhere in the output;
- the model reported each result, said only the user can change the sandbox, and did not retry.

My first live read test tested nothing (the tool does not expand `~`), so the second used an absolute path.

### Honest limits (also in the ADR)

- The model can still write the executable (it must, to build ask), so `/reload` stays user-typed.
- A check and its use are two steps for the file tools; `bash` is exact because Seatbelt checks at the operation.
- Write scope, network level and a read allow-list exist and are tested in the policy and compiler, but nothing
  configures them yet (roadmap 0042).
