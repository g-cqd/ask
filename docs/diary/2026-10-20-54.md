# Diary — 2026-10-20 (54)

## The real binary, driven with real mouse reports

Until now every pointer check was the controller driven by a test. This one runs the built `ask` in a pty, sends the bytes a terminal
sends for a press, a drag, a release and the wheel, and reads back what comes out: the screen through `pyte` (a terminal emulator) and
the OSC 52 copies from the raw output. `Scripts/probe-pointer.py`; no window opens and the clipboard is never touched, because the
terminal is announced as Ghostty or WezTerm, which take OSC 52, so `pbcopy` is not used.

| # | Claim | Result |
|---|---|---|
| 1 | The binary asks the terminal for mouse reports, and not when `ui.mouse` is false | **CONFIRMED** (`?1000h` and `?1006h` sent / not sent) |
| 2 | A drag highlights the dragged cells and copies exactly that text | **CONFIRMED**: columns 7 to 15 inverse, `Leave ask` copied |
| 3 | A backward drag across two rows reads them in order with the grapheme under the press | **CONFIRMED**: `Leave ask, stopping a running turn first.\n/fol` |
| 4 | A click clears; a double click copies the word; a triple click the line; typing clears | **CONFIRMED** |
| 5 | WezTerm gets its first copy twice and the next once | **CONFIRMED** |
| 6 | With `ui.mouse` false a drag selects and copies nothing | **CONFIRMED** |
| 7 | The wheel scrolls back to the start and returns to the end, and every row stays a whole line | **CONFIRMED** after a repaint |
| 8 | The probe can fail | a binary built with "typing keeps the selection" fails exactly that check (14 of 15); the restored one passes 15 of 15 |

### What went wrong

- **The first read after a wheel scroll looked like a rendering bug**: a row read `› /help-up  Queue a message…`, a prompt fused with
  another line. It was the emulator: the screen scrolls the transcript with scroll-down (`CSI T`), which `pyte` does not implement.
  Forcing a full repaint (a resize) and reading again showed every row whole. The probe repaints before it reads anything that scrolled.
- The triple click first returned nothing because the probe paused longer than the 400 ms double-click interval between clicks. The
  recognizer was right and the probe's timing was wrong.
- The negative control first produced no output at all: the probe passed a relative path to a process that changes directory before it
  executes. Fixed with an absolute path.

### Not verified

- **An emulator is not a terminal.** pyte reads the bytes ask writes; it does not tell whether kitty, Ghostty, WezTerm or Terminal.app
  draw and select the same way, or whether the clipboard really ends up with the text. Terminal.app and unknown terminals use `pbcopy`,
  which this probe deliberately does not exercise.
- **Tool folding is not in the probe**: a tool result needs a model and a provider, which the probe does not have. Folding is covered
  by the controller tests (diary 51) and by no real run.
- **tmux and ssh** are untested.
