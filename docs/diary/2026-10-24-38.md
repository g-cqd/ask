# Diary — 2026-10-24 (38)

## A regex kernel and AemiRegex: what the measurements say before anything is built

Worktree `ask-regex`. No Agora. The owner asked for a Sendable, safe wrapper over `NSRegularExpression` to remove the Swift `Regex`
overhead, then suggested a NEON assembly kernel for compiling and matching regexes, an x86_64 port, and the name `AemiRegex`, and finally
a document and report of what it would take. Nothing was built. The report is `docs/research/aemiregex-requirements-2026-10.md`.
Probe code is archived in `docs/research/probes/` (`IcuRegexGuardProbe`, `RegexKernelProbe`, `RegexKernelCodegen`, all `.swift.txt`).
Host load was about 11 to 20, so ratios are trustworthy and absolute times are not.

## Probe ledger

| Claim | Probe | Verdict |
|---|---|---|
| `NSRegularExpression` needs a wrapper to be `Sendable` | Compiled `func need<T: Sendable>(_: T.Type)` with it, Swift 6 mode | **REFUTED**: it already is |
| Swift `Regex` is the cost in `ask` | Searched the sources for every use | **Only partly**: one runtime place (three short patterns, an error path) and two test helpers. The 173 ms figure was for scanning 642 files, which `ask` does not do |
| Removing our `Regex` uses removes the dependency | `otool -L` and a read of Aemi's `SchemaNode.swift` | **REFUTED**: `libswift_StringProcessing` is linked implicitly and Aemi's schema code uses `Regex` |
| `NSRegularExpression` is exposed to catastrophic backtracking | `^(a+)+$` on `a…ab`, n = 18, 22, 24, 26 | **CONFIRMED**: 11.9 ms, 215 ms, 1.0 s, 3.8 s |
| A guard can bound it | `enumerateMatches` with `.reportProgress`, stop after 50 calls | **CONFIRMED**: 11 to 14 ms at n = 20, 26, 40 and 200 |
| The guard's count is deterministic | Same input twice, no cap | **CONFIRMED** for one pattern: 838 both times |
| A step budget is cheap to set | A benign 4 MB scan with the callback | **COMPLICATED**: about one call per input position (3,999,997 calls), so a budget must scale with input. Whether it then separates benign from catastrophic is **open** |
| Matching is a large share of an in-process search | 665 files in memory: regex 15.75 ms, SIMD first-byte prefilter 0.75 ms, `memchr` 0.45 ms; earlier, reading every file 13.7 ms | **CONFIRMED for regex, but the floor is I/O**: a perfect kernel saves at most about 15 ms per search |
| Assembly beats Swift SIMD enough to justify itself | SIMD16 loop against libc `memchr`, 2 MB | **NOT SUPPORTED**: 0.3 ms apart |
| The kernel needs a separate x86_64 port | `swiftc -emit-assembly` for both targets | **REFUTED**: one source gives `cmeq.16b`/`umaxv` (arm64) and `pcmpeqb`/`pmovmskb` (x86_64); AVX2 only with a flag |
| The x86_64 build gives the same answers | Built for x86_64, ran under Rosetta | **CONFIRMED**: 176 matches, 23,923 and 23,929 candidates, identical to arm64. Speed not measured (Rosetta) |

## Mistakes caught

- My first Rosetta check printed `rosetta=0`, which was the exit status of `head`, not of `arch`. Rerun properly (`arch -x86_64 /usr/bin/true`
  exit 0, then the x86_64 probe itself), it held, but the first line was not evidence and the report waited on the second.
- The probe's label "libc memchr (NEON in libc)" is wrong in the x86_64 run; the label is a property of the arm64 libc only.
- The first pointer arithmetic in the probe did not compile; no result came from that attempt.

## Not done, on purpose

No wrapper, no engine, no kernel, no Aemi change. The decisions the report lists for the owner (home, what "safe" means, syntax scope, whether `ask`
needs any of it now) change what should be built, and the roadmap entry 0058 records them as the blockers.
