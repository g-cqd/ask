# Diary — 2026-10-20 (29)

## A multi-line prompt (roadmap 0045)

Steering reached main as `65523a6`. The next unit is the editor: pasted line breaks used to become spaces, and
there was no way to type a newline. Now a paste keeps its lines, Shift-Enter or Ctrl-J starts one, and the
editing keys work per line (see 0045 for the list and for what is still owed: wrapped-line navigation).

## Cost (ADR-0016)

`cd Benchmarks && BENCHMARK_DISABLE_JEMALLOC=1 swift package benchmark --target RenderBenchmarks --filter '(frame/120x40 keystroke|editor/120x40.*)'`.
Wall time, p50 [p25-p75]:

| | Before | After |
|---|---:|---:|
| keystroke frame, 120x40 | 10 [9-10] µs | 8.9 [8.8-9.2] µs |
| Up/Down in a 100-line (6 KB) prompt | not comparable: it was a no-op, 125 ns | 109 [105-113] µs, first version |
| the same, one text-to-array conversion per move | | **58 [57-60] µs** |

The keystroke frame did not regress; I make no speedup claim (separate runs, one fewer string replacement in
paste). A vertical move is new work, found from line boundaries in the whole text; at 58 µs for a prompt far longer
than anyone types it is well inside the 2 ms input budget. Converting the text once per move instead of several
times took it from 109 to 58 µs, which is the only optimisation here, and it moved a number.
The "typing mid-prompt" benchmark was dropped from the comparison: before the change the cursor stayed at the end
(Up did nothing), after it sat in the middle, so the two measure different work.
