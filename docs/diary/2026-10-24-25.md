# Diary — 2026-10-24 (25)

## Selecting text in the input — roadmap 0051 and TerminalKit 0019, ADR-0076

### What changed

- `InputDrag` (press, head, edge), `ScreenController+InputSelection` (pointer, keys, the timer step), `PromptEditor.remove`,
  `PromptEditor+Keys` (`isDeletion`, `insertsText`), exact per-row highlights in `PromptLayout`, and the status line's copy hint for a
  selection in either place.
- A drag in the input highlights, moves the cursor to the dragged end, copies on release, and is replaced by typing or a paste; Backspace deletes it;
  other keys drop it. A drag held at an edge of a tall draft steps rows on the existing timer.

### Evidence

| Claim | Probe | Result |
|---|---|---|
| Both ends included, either direction; past the end; across lines; wide characters; leaving and returning to the pressed cell | `InputSelectionTests` (16) | Pass |
| Replace, delete, drop, copy and clear keys; a click clears; the transcript's selection is dropped; mouse off and a waiting question | same | Pass |
| The edge timer steps up a tall draft and stops; release stops it | same, with `rig.tick()` | Pass |
| The highlight of each row is exact | `PromptLayout` called directly | Pass |
| Real binary | `probe-input.py` (32 checks): a drag copies exactly the dragged text over OSC 52, highlights it, and typing replaces it in what the provider receives and the session records | Pass; expecting the wrong replacement fails |
| Other contracts | pointer 26/26, folding, code 9, runners 8 | Pass |

Eight mutants were caught (either end's character dropped, the cursor not following, typing and Backspace not replacing, the timer not
stepping, the highlight past a row). Four survivors were all informative, not misses: *the pressed-cell guard in `range`* was redundant with
the early return, so I removed it and added the "leave and return" test; *the past-the-end check* was redundant (the caret lookup already
gives the caret at or before the cell), so I deleted it; *the highlight one cell past a row* is invisible in cells, since the slicer only
cuts text, so it is now checked on the highlight values themselves; and an equivalent mutant of the prefix needs no test.

### Costs

The first version built a highlights array for every frame, selection or not. It now builds none unless something is selected.

Paired, interleaved, same harness, base (`b2f0eca`) then head, two rounds, allocations identical (7 for the cached composer):

| Round (one-minute load) | Keystroke frame p25/p50/p75 | Streamed line | Cached composer, 100 lines |
|---|---|---|---|
| 1 base (6.4) | 35 / 37 / 43 µs | 88 / 92 / 110 µs | 3,167 / 3,333 / 4,375 ns |
| 1 head (34.0) | 35 / 39 / 47 µs | 87 / 92 / 101 µs | 3,167 / 3,293 / 3,667 ns |
| 2 base (18.1) | 34 / 38 / 66 µs | 91 / 103 / 229 µs | 3,251 / 3,585 / 4,583 ns |
| 2 head (24.8) | 38 / 46 / 113 µs | 100 / 135 / 302 µs | 3,293 / 3,543 / 4,375 ns |

Round 1 shows no difference. Round 2 ran at a load of 18 to 26 and its tails are 2–3× round 1's, on both sides; head is higher there at p25
by 4 and 9 µs, which this data cannot separate from load. It is not evidence of either a regression or its absence; the code added to a
frame with no selection is one comparison and one empty-array check.

### What remains
