## The plan, written down

Eleven roadmap entries, `0005` through `0015`, covering what stands between 556 lines of scaffolding
and a working agent: the cross-repo blocker, the reset ladder, the session tree, the loop, providers,
tool execution, codemode, the render pipeline, the pixel measurement, and the compact UI.

Two orderings in that plan are counter-intuitive enough to be worth stating plainly.

**`0007` is blocked by `0009`.** The action-to-action budget measures Enter producing a prompt in a
program with no agent. It cannot be re-derived until the loop exists — and the instant the loop lands,
the stale number becomes *actively* misleading: a real measurement of the wrong thing, quoted in four
places. So `0009`'s acceptance is not "it runs". It is the loop **plus** a re-derived budget.

**`0013` and `0014` are one dependency.** Pixel chrome is drawn inside `RenderPipeline.flush()`. So
measuring what pixels cost and adopting the renderer that draws them cannot be split without building a
renderer twice.

## The pixels are already there

Probed the source rather than the roadmap, and it changed the shape of the work.

`PixelChrome` is implemented, byte-tested, and already called from `RenderPipeline.flush()` — between
the cell diff and the cursor move. It has **three** primitives, and the third is the one that matters:
`.bar` places a `widthPixels × heightPixels` rect at a pixel offset inside its cell, so a proportional
scrollbar is **one placement costing zero columns** instead of four characters.

None of it is used by `ask`. `AskTUI.swift:41` calls `connection.getSize()` and discards the result —
discarding `pixelWidth`/`pixelHeight` along with the columns and rows.

What blocks it is not missing code. It is missing measurement, in a specific and slightly awkward way:
**no environment variable carries a cell size.** `supportsPixelChrome` needs
`supportsKittyGraphics && cellPixelSize != nil`, and the second half can only come from
`ioctl(TIOCGWINSZ)`. So the env-var guesswork that roadmap `0003` plans to replace is not merely
unproven — it is *insufficient* for this feature, and `0014`'s measurement is a prerequisite for `0003`
rather than a consequence of it.

## The launcher passed when nothing was measured

`Scripts/verify-chrome-cost.sh` as first written exited **0** after every terminal failed to launch, and
printed a column of `?` for terminals that had reported.

That is the same defect TerminalKit's first emulator harness had, and it cost that project a wrong
ADR-0002 before the harness itself was caught: a quoting mistake turned every tier into a no-op, and it
reported PASS for all three. A harness that passes when it should fail is worse than no harness, because
it manufactures false confidence.

Probed both directions after fixing it:

| Condition | Before | After |
|---|---|---|
| nothing launched | exit 0, table of `?` | **exit 1**, `RESULT: INCONCLUSIVE` |
| partial run | exit 0 | **exit 1**, `RESULT: PARTIAL` — missing terminals are unmeasured, not zero |
| all reported | exit 0 | exit 0 |

Three parsing bugs came out of the same exercise, none of which I would have found by reading the script:
`DRAWABLE` printed `:` because the value is field 4 not field 3; `VERDICT` printed `?` because the
verdict sits two lines under its heading and is `**`-wrapped; and a `NO_TTY` report rendered as `?`
instead of naming itself.

## This environment cannot produce the numbers

**No controlling TTY here.** Probed: `pty.fork()` plus `TIOCGWINSZ` returns
`rows=0 cols=0 pixelWidth=0 pixelHeight=0`, and reading fd 0 fails `ENOTTY`.

So `0014`'s live numbers are still owed. What *was* verified here is that the probe behaves correctly
in all three paths — `NO_TTY` as a named result, real pixels with a matching env guess, and real pixels
where the env guess is **wrong** (the third path is `0003`'s claim, measured rather than argued).

The chrome byte cost in the report is explicitly labelled an estimate from the encoder's shape. It is
not a measurement and must not be quoted as one.
